后续状态：用户明确只用于比赛演示；已实施生产模式拒绝启动、撤权标题修复、登录撤销和资源准入等加强，见[后端加强记录](BACKEND_HARDENING_20261102.md)。下文保留当时审查发现与原始探针结果，不代表这些问题全部仍未处理。

本轮只增加审查探针与本文，没有修改生产逻辑、主库数据或服务配置。探针在独立tax_harness_test数据库运行，不调用收费模型。

## 2. 已有保护与本轮验证

- 身份从登录Cookie经服务端查询获得，业务接口不直接相信客户端传入的角色；但这不能弥补模拟登录入口。
- owned对会话、轮次、任务等绑定user_id，企业读取/写入由user_company_grants检查。私有知识资料还检查owner；授权企业共享资料与企业业务数据按权限共享，不是每个用户各存一份。
- 来源、文档版本、检索引用与观测详情有有效性与权限检查；撤权/版本变化可拒绝旧执行。标题列表是已复现的不一致入口，不能宣称所有入口已完整统一。
- 保存使用数据库事务、行锁、expected_revision、操作账本及幂等键。任务执行使用租约、fencing_token、run generation，旧执行不能在接管后继续提交。
- 同一用户当前只领取一项活动工作，多个用户可以同时被领取。用户级串行有助于一致性，但不是整个系统无限并发。
- 本地推理有锁、请求ID核对、超时与重启保护；现有并发响应关联测试保留，不将结果正确关联等同于压力容量充足。

## 3. 仍需明确的真实部署边界

- **私有与共享**：会话、偏好、本人私有文档按用户隔离；企业发票、规则、正式发布的企业资料按企业授权共享。另一个被合法授权用户看到同企业发票不是越权。真实客户/组织的权限分配与管理流程目前未完整建模。
- **单浏览器多账号**：同源Cookie通常共享，多个标签切换账号不是两套独立登录容器。后端按每次请求的Cookie身份执行；若产品要求同一浏览器同时使用多个账号，需要额外设计，不能依赖页面显示的用户名判断身份。
- **数据库防御纵深**：运行角色有广泛表级SELECT，未发现数据库行级隔离策略，主要依赖应用查询条件。不是已证明的跨用户越权，但单点漏写过滤的后果较大。真实多组织部署可增加数据库层隔离，并让迁移/管理员凭证与服务运行环境分离。
- **排队公平性**：任务领取按user_id扫描，不按所有用户最早等待时间选取；持续高负载可能导致等待分配不公平。这是源码推断，未做长期饥饿复现。
- **请求体和资源**：文件上传有实际字节上限及解析/OCR边界；现有中间件未统一覆盖普通JSON请求。字段长度校验发生在解析后，不等于网关级请求体上限。还需总请求体、处理时限、检索/导出和推理排队的资源策略。
- **部署和恢复**：现有默认启动监听127.0.0.1；没有在本轮测试真实HTTPS反向代理、滚动部署、多台机器、节点断网、数据库主机故障及持续高峰流量。程序恢复用例与生产备份的可恢复性、允许丢失范围和恢复时间分别管理。
- **模型服务**：API调用按请求构造独立payload，未看到把不同用户拼成同一对话的全局状态；实际选中内容会发送给所配置的模型服务。外部模型服务自身的保存与隔离行为不是本仓库代码能够证明的。

## 4. 建议的落地顺序

第一批，建立可信身份与完整可见性：生产/演示模式边界、真实登录及会话撤销、修复撤权标题，并为所有资源做跨用户、跨企业、撤权后的接口矩阵。验收以不能伪造身份、不能从任一入口读回失去权限的内容为准。

第二批，控制并发与失败成本：请求准入、用户与全局队列上限、公平调度、模型/推理并发和累计用量限制、超时取消及数据库等待反馈。继续保留版本冲突和幂等守卫，不用去掉锁换低时延。

第三批，按目标部署验收：固定机器、worker数量、数据库和模型配置，逐级增加并发与长时间混合负载，实际演练重启/断连/撤权/恢复。正确性、隔离和可恢复是硬门槛；响应时延以可用性和排队反馈为准，不追求任意1秒目标。测试数据必须独立，真实模型成本单独控制。

本轮审查探针位于`backend/tests/_production_probe.py`，按文件显式执行，不混入原默认功能用例总数。后续修复时应把上述“缺陷复现”改为相反的安全验收断言，而不是保留它们来宣称生产就绪。
