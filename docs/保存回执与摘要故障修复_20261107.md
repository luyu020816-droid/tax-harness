# 保存回执与摘要故障修复

已修复 `SUMMARY_INVALID` 遮蔽已保存回执的问题。代码仍在本地 feature_adjust_1107，未提交、未推送。原始失败证据保留，没有改写修复前验收成绩。

后端指纹：`828e6851a68e0027e7a8081853a04712d3343c7cd52fdc33a54ffcc7636dc045`。

## 问题与行为变化

修复前：F002 用途已提交、revision 从 1 到 2、回读已核验，但后续摘要校验报错。Runtime.fail 只保存错误，final_message 为空、final_cards 为空，用户须进入账本才能确认已经保存。

修复后：

- 摘要候选仍严格校验，无效候选不发布。
- 摘要无效时尝试取消本轮的提前压缩，使用完整原始历史继续。只有原始历史全部保留且不超过原硬预算时才继续；没有放大预算、静默丢弃历史或将坏摘要当作有效摘要。
- 如果仍因 SUMMARY_INVALID 或上下文容量问题停止，宿主独立读取本轮、本人的已提交操作并生成真实回执，持久化答复和来源，记录 failure_receipts_delivered 事件。
- 失败状态及真实错误保留，答复明确说明后续未完成；页脚显示“保存回执已交付，后续未完成”。不会因此将其他遗漏事项标成 completed。
- 正常答复和故障回执复用同一个程序渲染函数，保留“核验待完成”“当前值后来已变化”等区别，不能把 pending 升格成 verified。
- 交付前仍检查租约、fencing token、memory_epoch、来源归属和权限。撤权、旧执行或无真实提交时不生成保存成功回执。

此改动解决的是保存回执对摘要失败的依赖，不保证模型以后不再产生无效摘要，也不覆盖任意类型的进程或数据库故障。真实未完成事项仍按失败或待办理处理。
