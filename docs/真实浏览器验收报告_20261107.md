## 失败：08 保存提交后，摘要失败阻断回执交付

输入为“把甲企业F002的用途填写为办公耗材采购”。浏览器验收有意在服务端处理完毕后丢弃受理响应，以验证响应丢失后的状态与重复请求。

实际发生：

- F002 用途真实落库，revision 从 1 到 2，操作状态 committed、回读状态 verified。
- 随后摘要处理返回 `SUMMARY_INVALID`，整轮状态变为 failed，final_message 为 null、final_cards 为空。
- 刷新原会话可见“本轮未能完成”；点击“核对已提交操作”，能在实际账本中查到这一笔已提交操作。
- 反复原样重放同一 client_request_id 返回同一失败 turn_id，仍然只有一笔已提交操作。幂等核对通过；失败轮次的正常回执交付没有通过。
- 丢弃响应时界面直接显示英文 `Failed to fetch`，自然表达与恢复指引也有改进空间。

轮次：`fa8b4112-b211-4272-bd7b-9eca5f72f05c`。

操作：`e9600ae8-0cbe-4201-b54c-55e50237b155`。

证据：[最初原始记录](../.local/evidence/browser-acceptance-20261107-02/08-lost-response-raw.json)、[重复请求与完整运行证据](../.local/evidence/browser-acceptance-20261107-02/08-replay-evidence.json)、[原始断网提示截图](../.local/evidence/browser-acceptance-20261107-02/08-failure.png)。

这是已发生的失败，不能因数据库保存正确或后来续办成功而判定本轮完成。建议后续将已提交回执的交付与可失败的摘要处理分离，并在失败答复中明确“已保存的事实、未完成的处理及核对入口”。本次验证没有实施该修复。

## 测试脚本问题与复核方式

首轮浏览器记录为 18 通过、2 失败、1 未运行。12a 的失败断言错误地在引用元数据中查找 Q7421/R8532，而产品按 citation_id 加载原文。已另通过实际原文 API 和页面渲染核对两个候选，复核记录为通过。原报告未覆盖，依据见 `12a-reviewed-evidence.json`。

08 的原始脚本还把网络错误预期写成中文“无法连接业务服务”，实际显示英文 `Failed to fetch`，因此没有继续完成脚本中的点击重试。随后另用原始请求标识复核了后端幂等及已提交账本，但未将此转写成浏览器点击重试已通过；08 仍然失败。

补充证据脚本先后修正了失败页按钮名称及折叠区定位，这些是截图脚本定位问题，不计为产品故障。没有为改善通过数修改产品、预期金额、权限约束或原始模型失败记录。

最终结果由原报告、原文复核、独立 SQL 及第 13 项补测合并，保留不同来源，不代替用户签收。
