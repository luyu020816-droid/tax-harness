# SPEC：独立聊天语义索引与混合召回

版本：1.0；日期：2026-11-04；状态：核心实现已完成，默认 off，S5 启用验收待完成。

适用项目：tax-harness；基线分支：`feature_adjust_1031`；基线提交：`47fd128`。本文件是后续开发依据，不代表能力已上线或验收通过。实施前核对同伴提交与迁移号，不提交既有无关改动。

## 1. 问题与目标

当前普通聊天与知识库已经隔离。当前会话采用追加日志、预算投影与摘要；旧聊天由`search_conversations`查找、`read_conversation`回读。当前历史搜索只有日期和中文词法路径。

[专项验证](../../CONVERSATION_ACCEPTANCE_20261104.md)中，固定改写查询直接提交检索层时为0/10，而日期20/20、词面10/10、多候选10/10、无答案10/10。该结果说明当前直接检索缺少语义匹配能力；它不是包含Agent查询改写的端到端准确率。已有60题标签由Agent拟定，仍待人工确认，不能称人工留出。

本次解决：用户换一种说法时，能定位本人仍可访问的相关历史，并提供可核验原文。例如原文“数据库迁移前先备份并保留回退副本”，问题“之前数据库搬家的方案是什么”。

本次不承诺任意表达100%召回，也不把相似片段当作正确答案。找不到、多候选、覆盖不足分别处理。

## 2. 范围与不可变约束

### 2.1 本次包含

1. 聊天专用分块、向量索引、后台增量作业和历史回填。
2. 日期/词法/语义路径、候选融合、可选重排和可校准的弃答。
3. 原文回读、相邻消息导航、稳定分页与引用失效检查。
4. 用户/企业隔离、来源变化、删除撤权、索引故障和重启恢复。
5. 沿用现有页面风格的来源卡片及运行洞察增量。
6. 开发集、独立人工确认留出、真实模型与故障验收。

### 2.2 本次不包含

- 不把聊天写入`knowledge_documents`、`knowledge_chunks`或知识向量表。
- 不修改财税规则生效、企业授权、发票保存、幂等或恢复协议。
- 不实施自动偏好挖掘、偏好候选确认、每日总结或记忆图谱。
- 不增加外部向量数据库、embedding API key、通用搜索平台或新主导航Tab。
- 不恢复固定最近N轮，不自动按时间删除原文，不将摘要替代原文索引。
- 不开放生产认证，不将本次设计宣称为比赛官方新增要求。

### 2.3 必须始终成立

| 编号 | 约束 |
|---|---|
| I01 | `sources`原文和`conversation_events`仍为权威追加记录；索引可丢弃重建。 |
| I02 | 聊天与知识共用模型权重可以，共用候选语料、引用授权或业务规则状态不可以。 |
| I03 | 搜索仅能处理调用者当前可访问的消息；检索、回读、交付和前端刷新均重验。 |
| I04 | 引文只能来自真实原文位置；embedding输入前缀、摘要、查询改写不得变成原文。 |
| I05 | 历史用户指令不是当前写入授权，历史助手建议不是用户确认或业务回执。 |
| I06 | 索引失败不阻塞消息持久化，不更改原文，不无限重试。 |
| I07 | 失效来源即使向量或缓存尚未清理，也不得再次被交付。 |
| I08 | 候选数量和分块长度不是历史保留上限；无明确日期时不默认只查最近一个月。 |
| I09 | 维持当前模型输入预算和工具/步骤上限；新增搜索不能把整段历史无界装入模型。 |

## 3. 方案选择与现有能力复用

| 方案 | 优点 | 局限 | 决策 |
|---|---|---|---|
| 仅由模型改写关键词再做词法搜索 | 改动少，可保留为Agent策略 | 改写不一定生成原词，结果受模型判断影响，无法补足底层能力 | 不作为本次主方案 |
| 纯向量搜索 | 支持不同说法 | 编号、否定、例外及无答案容易误匹配 | 不单独采用 |
| 词法＋向量＋原文核验 | 保留精确定位并补语义候选，可分别评测 | 需维护索引版本、覆盖状态与质量门槛 | 采用 |

保留PostgreSQL和已安装的pgvector。复用`retrieval_engine.py`中固定版本的本地embedding、token计数、向量合法性检查及可选reranker；复用`retrieval_process.py`的进程隔离与既有资源保护。实施前通过安装清单核对模型版本、1024维和实际权重，不以模型别名代替指纹。

旧`history_jobs.py`、`history_passages`和`history_embeddings`已有历史实现，但在线入口明确停用，旧来源集合与当前策略不一致。本次只借鉴纯分块、租约和推理调用逻辑；不启用旧开关，不直接导入旧向量，不恢复知识接口的`corpus=history`入口。

## 4. 总体链路与模块接口

```text
消息先写入原始日志
        ↓ 消息达到可索引状态
同事务登记作业／后台补偿扫描
        ↓
原文分块 → 本地embedding → 校验完整性 → 原子发布索引代次

搜索请求 → 固定用户/企业/时间/来源水位
        ├─ 日期枚举（无查询词时）
        └─ 词法候选 ＋ 授权集合内向量候选
                   ↓ 原文与依赖重验
                融合 → 可选重排 → 支持度判定
                   ↓
             冻结候选页 → 原文引用／相邻消息回读
```

外部仍使用两个Interface：`search_conversations(...)`和`read_conversation(source_id, char_start)`。Agent不选择用户身份、索引代次、模型版本或后台作业状态。

内部Module职责：

| Module | 职责 | 对外需要了解的内容 |
|---|---|---|
| `conversation_history.py` | 现有检索/引用外观、输入与权限检查、分页和引用持久化 | 现有搜索与回读Interface，新增可选模式和覆盖状态 |
| `conversation_index.py`（新增） | 来源适格、分块、profile、索引读写与原子发布 | 可索引来源、索引覆盖及候选读取 |
| `conversation_jobs.py`（新增） | 幂等入队、领取、续租、重试、回填和停止 | 作业生命周期，沿用现有应用启动/停止模式 |
| `conversation_retrieval.py`（新增） | 各路候选、融合、重排、支持度和弃答 | 候选及诊断；不自行生成最终答复或业务修改 |

不新建另一套Agent Runtime。分块若复用旧纯函数，应有当前版本包装与回归，不顺带重构旧历史实现。

## 5. 数据设计

新增迁移拟为`015_conversation_semantics.sql`；当前基线最大迁移号14，实施前按实际空闲号顺延。新表名称与旧历史、知识表分开。

### 5.1 `conversation_index_profiles`

保存不可变索引定义：`profile_id`、`inference_profile_id`、`model_manifest`、`dimension`、`chunker_version`、`input_format_version`、`created_at`。

`profile_id`由推理安装指纹、维度、归一化方式、分块和输入格式共同计算。只要其中一项变化，建立新profile，不覆盖旧定义。v1固定1024维，不在本次增加多维度适配层。当前提供服务的profile由部署配置选择，不能用用户请求指定。

### 5.2 `conversation_index_jobs`

核心字段：

| 字段 | 含义 |
|---|---|
| `(source_id, profile_id)` | 幂等唯一键；关联原消息与索引定义 |
| `source_revision, source_hash` | 本次作业期待的原文版本 |
| `state` | `queued/running/ready/failed/cancelled` |
| `target_generation_id` | 当前构建的索引代次 |
| `published_generation_id` | 可读代次，未完整发布时为空或保留仍有效旧代次 |
| `expected_chunk_count` | 发布前核对完整性 |
| `attempts, next_retry_at, last_error` | 有界重试和脱敏错误 |
| `lease_until, fencing_token` | 防并发重复领取及旧worker晚到发布 |
| `created_at, updated_at` | 运行追踪 |

重建中的状态不等于已发布代次失效；可读性必须同时满足profile匹配、来源有效、原文hash和已发布代次匹配。不能只根据`state='ready'`推断所有历史已索引。

### 5.3 `conversation_passages`

字段：`passage_id`、`source_id`、`source_revision`、`source_hash`、`profile_id`、`generation_id`、`ordinal`、`char_start`、`char_end`、`excerpt_hash`、`embedding_input_hash`、`embedding vector(1024)`、`created_at`。

- 唯一键：`(source_id, profile_id, generation_id, ordinal)`。
- 建立来源/profile/代次索引。v1先在授权集合内精确向量排序，不直接加入全库ANN近似索引。
- 候选原文从`sources`按位置读取；不额外复制一份消息正文为权威文本。
- 所有位置为Python Unicode字符索引，左闭右开；不是UTF-8字节或JavaScript UTF-16位置。SQL substring要显式转换为一基下标。
- 发布和引用均验证位置、截取内容hash与来源hash；数据库不能完成的跨表约束由事务内校验保证。
- 索引清理不级联删除原消息或现有引用。引用继续指向原消息与位置，不依赖passage永久存在。

用户/企业过滤依据原始消息、会话和当前授权关系，不能信任向量行中复制的授权快照。v1不为全文向量过滤添加用户可传入的`user_id`。

## 6. 索引来源与分块

### 6.1 适格来源

仅索引能通过现有`conversation_log.read`及当前会话可见性检查的聊天消息：

- `user`：所属轮次已结束，包含完成、等待用户，以及明确失败/取消/中断后仍有效的原始用户输入。
- `assistant`：仅索引实际发布、由`final_response_ref`确认的最终回复；继续重验其知识及来源依赖。
- 不索引运行中的消息、工具正文、草稿、摘要、正式状态包、规则表或上传文件正文。
- 删除、停止召回、hash损坏、当前无授权、依赖失效的来源均不适格。
- 归档消息仍可由本人主动检索，不自动取消归档。

消息写入不等待embedding。待处理消息可以进入当前会话上下文，但不因此宣称已进入跨会话语义索引。

### 6.2 分块规则

v1采用可解释的原文切片：短消息整条；长消息目标最多600字符、最多1200个实际token，重叠最多60字符。两种限制取更严格者，token计数包含实际送入embedding的前缀。上述是本项目初始参数，需开发集验证，不是DSH的参数或性能结论。

- 每块只属于一条消息，不跨用户、企业、消息角色拼接。
- 分块必须覆盖全文；首块从0开始，末块到原文末尾，无空块、越界或前进停滞。
- 分句只改善切点，不丢弃否定词、例外、编号、标点或重复内容。
- embedding输入只加固定角色说明，不用LLM改写原文，不把摘要作为索引正文。
- 角色前缀及后续检索上下文不是引文的一部分，`embedding_input_hash`与`excerpt_hash`分开。

诸如“就按第二个”的短消息，不能承诺单条向量能理解其指代；由第9节的相邻原文导航补足上下文，不预先拼接成未经核验的新事实。

## 7. 后台增量、并发与故障

### 7.1 入队与补偿

在轮次正式结束的事务中，对适格来源幂等登记作业；覆盖正常结束、失败、取消和恢复结束路径。不能只在`add_source`时入队，否则会漏掉稍后才适格的消息或索引未发布回复。

增加补偿扫描：查找适格来源与当前profile作业之间的缺口，分页登记。不得仅靠“最大已索引event_id”跳过更早尚未完成的来源。后台分页大小不构成总历史上限。

### 7.2 作业状态

```text
queued → running → ready
             ├─ 暂时故障且未达上限 → queued（退避）
             ├─ 达到上限／不可恢复错误 → failed
             └─ 来源不再适格 → cancelled
```

初始最多3次尝试，前两次失败分别至少退避30秒、120秒；达到上限保留错误，修复依赖后由显式运维命令恢复。重启通过租约到期接管，递增fencing token；旧worker不能发布。

### 7.3 原子发布

1. 领取作业，捕获来源revision/hash、profile及target generation。
2. 事务外执行有界分块和embedding，沿用固定版本模型、进程隔离与合法向量检查。
3. 允许分批落地构建中片段，但它们不可被搜索到。
4. 发布事务按既有锁顺序锁定必要状态，复核租约、来源、原会话、授权与知识依赖，核对块数、位置、hash和向量维度/有限值。
5. 仅完整成功后更新`published_generation_id`并标记ready。失败不得移动发布指针或覆盖仍有效的旧代次。

删除或撤权先提交时，晚到发布必须拒绝；发布先提交时，后续查询也必须立即因当前状态失效而拒绝。不能把索引清理速度当作权限保证。

### 7.4 资源保护

复用现有本地推理保护，后台小批量处理，在批次之间让出资源给交互查询。不同时为聊天再加载一套大模型或增加无界线程。沿用现有准入、RPC、SQL和轮次超时；超时后的后台结果仍须受租约/来源守卫，不能靠取消Python等待假装底层工作已结束。

已知原生推理崩溃根因仍开放。本次不声称修复它；必须验证模型退出、超时、连续失败及重启后词法回退和原文读取仍可用。

## 8. 搜索流程与排序

### 8.1 硬过滤先于内容交付

冻结调用者身份、明确企业、会话ID、日期、`before_source_seq`和`through_event_id`。复用当前词法路径的`SESSION_VISIBLE`及来源状态规则。

向量路径必须在同一授权集合、有效来源hash和当前已发布profile/代次内排序。不能先对全库取TopK再过滤用户；这既可能漏召回，也会扩大错误处理风险。复杂助手依赖还要通过原文读取守卫重验，必要时补取下一批有效候选；预算不足时标记partial。

词法路径继续提供当前可读原文的及时查询，不以“尚未生成向量”为由隐藏原来可读的消息。向量路径额外要求第6节的可索引状态；尚未终结的轮次不得算作已完成语义覆盖。当前输入仍遵守来源水位排除，不作为自己的历史命中。

明确编号、企业和日期不得被语义相似度覆盖。对可确定的精确编号应用原文字面约束，不因F003更相似而把它当F002。用户未明确日期时，不能默认丢弃两个月前的消息；不通过简单“最近优先”替代相关性。

### 8.2 路径选择

| 请求 | 行为 |
|---|---|
| 无query的日期/会话浏览 | 沿用完整时间线分页，不调用embedding或reranker，不改成TopK搜索 |
| 明确编号或词语 | 保留精确词法命中，语义只补充候选，不能挤掉精确编号对应结果 |
| 不同说法的主题查询 | 同时执行词法与向量路径，再融合与核验 |
| 语义索引未完成/模型不可用 | 返回可核验词法结果并说明partial/degraded，不能假装已做完整混合搜索 |

### 8.3 融合与重排

初始每路取最多30个不同来源候选；同一来源多个片段先保留最佳相关片段并记录其他命中位置，避免一条长消息占满结果。

采用基于排名的融合，初始RRF参数60，避免直接相加量纲不同的词法分数与向量分数。融合后最多20个候选进入可选reranker，首次展示仍默认5条、最多10条。参数属于开发初值，冻结后才运行独立留出；不依据留出分数反复调整。

reranker只接收已核验可访问的原文片段。它失败时，不允许把缺失的支持度分数当通过；若无经验证的无reranker策略，则语义独有候选不自动交付，保留词法结果并提示降级。

向量最近不等于相关。语义独有候选必须通过开发集校准的支持度策略；策略文件记录profile、阈值、开发数据hash和版本。不得写一个未经测量的“相似度0.7”就上线，也不能让无答案问题总返回最近的一条。

v1支持度采用`dense_score >= dense_min`且`rerank_score >= rerank_min`。开发集同时包含相关原文与无答案/近似编号/否定反例，枚举实际开发分数之间的阈值组合：在无答案误交付为0的组合中优先最大化正例Hit@5，再最小化误交付候选数，最后以固定数值顺序打破平局。保存选择过程和原始分数；若不能同时满足开发约束，不生成可上线策略。独立留出仅用于验收，不用于再次调阈值。无reranker回退必须有单独验证的策略；否则只做明确的词法降级。

精确数字/否定关系仍以原文为准。检索器负责相关资料，不替用户执行推理结论或业务修改。

### 8.4 候选不足与无答案

- 支持不足：说明当前范围未定位到可靠匹配，可追问主题、时间或会话。
- 多候选：返回候选或请求选择，不仅凭排名替用户决定“采用哪套方案”。
- 索引缺口或查询未完成：partial；不是完整的not_found。
- 即使索引覆盖完整，有限候选搜索也不能证明用户从来没说过；文案只说明本次没有定位到匹配。

不在本批加入自动LLM查询扩写。Agent已有主动改写可以保留，但检索层评测与Agent改写评测分开计量，避免掩盖底层缺口。

## 9. 原文引用与相邻消息

沿用`conversation_search`、`conversation_evidence`、`history_quote`和现有citation_id交付方式。最终引文按原文hash、revision和字符位置重验，不允许模型根据向量结果重写引文。

`read_conversation`在原有结果上增加最多前后各一条可读相邻消息导航：`source_id/role/created_at`。只返回导航，不自动装入整段历史；Agent仍通过现有回读工具获取正文，受原文分页和本轮模型/工具预算限制。

- 邻居来自同一原会话，逐条核权，并继承企业、来源水位和明确日期硬限制。
- 不返回不可访问邻居的ID、标题、正文或数量提示。
- 邻居ID不是已入模原文证据；未实际回读前不能生成引文。
- 助手与用户角色分开显示，历史建议不等于当前确认；当前业务状态要重新查询。
- 来源已删除、撤权或依赖失效，引用和已展开文本继续沿用现有前后端失效清理。

## 10. 搜索Interface、分页与覆盖语义

### 10.1 输入兼容

现有`/api/v1/conversations/search`与同名工具增加可选`mode=auto|lexical|semantic`，默认auto；原`query/session_id/date_from/date_to/cursor/page_size`含义不变。无query时仍走时间线。

`semantic`不能绕过部署开关：off或shadow时不向用户开放实验结果，只返回明确降级状态。用户不能通过mode启用后台作业或切换profile。

`read_conversation`保留原输入字段，不新增一个重叠的历史工具；邻居导航为可忽略的响应增量。旧知识混合入口继续403。

### 10.2 响应增量

维持原有kind、matches、citation和定位字段，补充：

- `retrieval_mode`：`date/lexical/hybrid/semantic`。
- `coverage`：当前授权范围内适格来源数、当前profile已发布数量、待处理/失败数量和来源水位。
- `degraded_reason`：例如embedding不可用、索引未完成、查询超时、支持度策略不可用。
- `status`：`ok/not_found/partial/unavailable`，沿用错误与交付守卫扩展，不让旧渲染器误解partial。
- `candidate_limit_reached`及候选页信息；分数和内部参数进入受控洞察，不全部塞进模型输入。

覆盖按授权范围和固定水位计算，不能用单个最大已完成ID宣称无缺口；不得暴露其他用户/企业的总量。索引覆盖完整与检索召回完整是不同概念。

### 10.3 分页

日期浏览保持现有event顺序游标。旧已签发游标按其原版本处理，不以新算法重新解释。

混合/语义分页在`history_queries`中使用`kind=conversation`及新的计划版本，冻结有界的候选来源/片段引用、排名、查询参数、profile、策略版本和来源水位；后续页面不重新embedding或重排。游标绑定用户和所有参数，不能跨用户或改参使用。同分候选采用固定排序键，避免数据库执行顺序改变页序。

每页及引用交付重新核权，删除/撤权的候选不得展示，不从旧缓存恢复。新消息或晚到索引不插入旧候选页，重开搜索才参与。profile/策略切换导致游标不兼容时明确拒绝并要求重新查询，不能混用两代向量分数。

查询及诊断缓存至少绑定用户、规范化过滤条件、来源水位、profile、策略和query hash；包含原文的embedding缓存还要绑定来源归属与输入hash。任何缓存命中都不能跳过当前权限/来源重验，不跨用户共享候选页或私有调试正文。

候选展示完毕不等于全部历史已遍历。对排名检索，界面说明“本次候选展示完毕，可调整描述继续查”；只有日期完整枚举才使用“历史浏览末页”语义。

## 11. 开关、观测与UI

新增单一部署模式：`CONVERSATION_SEMANTIC_MODE=off|shadow|on`，初始默认off。

- off：当前词法/日期行为，不自动启动新索引器；可使用显式CLI回填。
- shadow：构建索引、记录混合候选用于验证；用户仍收到当前词法结果，不假称语义已开放。
- on：使用通过门槛的profile和支持度策略，失败按第8节明确回退。

模型目录复用现有固定安装，不修改真实`.env`的密钥。历史旧开关保持停用，不能重新赋予它们第二套含义。

就绪信息区分主数据库、语义表/模型、当前profile及覆盖状态。语义不可用不破坏日期/词法和原文回读；不得把知识库ready当作聊天索引完整。

运行洞察沿用现有Tab，增加以下真实阶段与元数据：

1. 范围核验、query embedding、词法/向量候选、融合、重排、证据回读。
2. profile/策略版本、各路候选数、覆盖、降级、失败与过滤原因。
3. 本地embedding/rerank耗时、文本数量与实际token数；与远端LLM供应商usage分开。
4. 本地推理不虚构API Token费用或计算成本；原文/候选诊断仍遵守权限，不记录密钥。

UI维持现有配色、字体、间距、来源卡片和运行链路形式。仅增加必要的“聊天历史／原角色／原日期／覆盖不足”提示及邻居导航；不增加新知识库页面或主导航。桌面、390和768宽度验证，抽屉动画完成后检查无遮挡、引用失效后正文清理。

本项目时延目标是可用性。测量冷启动和热查询，验证有界资源与失败反馈，不为压缩少量耗时删掉核权、原文核验或引用步骤；频繁超时则不能切on。

## 12. 迁移、回填与回滚

1. 明确维护窗口与当前活动任务，备份原文、会话、事件及现有引用，并实际恢复到隔离库核对指纹。
2. 只新增聊天索引结构，不重导比赛样例，不迁移旧历史向量为新结果，不改原文、消息角色或业务表。
3. 以off部署新代码；增加显式CLI：`conversations-index backfill/status/retry`。命令实现须校验目标库，重置仅允许既有隔离测试白名单。
4. 通过当前来源适格规则幂等回填；记录逐范围缺口、失败及profile，不用“queued数量为0”冒充全部成功。
5. shadow验证新profile。模型或分块升级新建profile，不原地覆盖已发布数据；切换前验证质量及覆盖。
6. 满足第14节才开启on。原文仍留在当前数据库，不因建向量额外外传到第三方。
7. 回滚优先off并停作业，恢复当前词法/日期路径。已签发引用在原文仍有效时继续可读，不因停用向量而无故失效。

无须为功能回滚覆盖主库备份。若确需恢复旧备份，先维护、核对升级后新增数据与匹配代码版本；不能宣称恢复备份等于保住备份之后全部消息。

## 14. 验收与证据

### 14.1 程序与故障门槛

适用用例全部通过，以下安全/原文负例0例错误成功：

- 分块：空消息、长消息、中文/emoji、边界否定与跨块编号；重建片段覆盖全文，引用字符位置准确。
- 数据：原始内容与事件不可变；知识资料计数不因聊天索引增长；工具/草稿/未发布助手内容无索引。
- 作业：重复入队、双worker、重启接管、连续失败、坏向量、部分片段成功、模型退出及查询超时。
- 发布：推理期间删除会话、停止召回、撤权、知识依赖停用、profile切换；旧worker晚到不能发布。
- 检索：原有20项权限/失效矩阵全部保持通过；扩展query缓存隔离、邻居越界、跨用户游标、分页中失效和候选不足负例。
- 引用：伪造ID/原文/位置拒绝，未回读邻居不能引用，已展开正文失效清理。
- Runtime：历史中的保存指令、旧确认、助手成功声明都不能授权本轮业务写入；保存幂等、租约和规则更新回归无退化。

关闭问题必须记录原始反例、修改及复验，不通过放宽原文/权限检查提高通过率。

### 14.2 检索质量

现有60题和已见0/10转为开发/回归资料，不再作为新留出。准备并由人工确认一套新的60题：日期20、不同说法20、无答案10、多候选10。包括否定、更正、相似编号及较早消息；冻结问题、原文、适用角色/范围与相关来源集合后，不参与调参。

在同一数据、模型安装和授权条件下比较：纯词法、纯语义、混合。分别报告直接检索和实际Agent改写后的结果，不混分。

切on的初始门槛：

| 指标 | 门槛 |
|---|---|
| 新留出20题不同说法Hit@5 | 至少18/20；同时报告MRR和Recall@5 |
| 日期枚举与既有精确词面回归 | 日期20/20与原精确词面10/10不退化 |
| 新留出无答案自动交付不相关候选 | 0/10；不足支持须弃答或澄清 |

| 数据完整性 | 原字段指纹一致；源ID精确回读与hash一致 |

这些是项目拟定发布门槛，不是已有成绩。未达标保留off/shadow，记录失败并使用新的后续留出验证改进，不重复用已看答案的数据宣称泛化。

### 14.3 真实Agent与可用性

至少12类明确预期的场景各三次：同义表达、早期方案、两个月日期、长消息边界、指代展开、用户更正、助手建议未确认、多候选、无答案、索引未完成、撤权/删除、历史注入。先评判每题第一次结果，重复结果用于稳定性，不冒充36个独立题目。

核对最终文字、原文卡片、角色/日期、实际工具与数据库结果。记录完整模型请求、摘要、修复、失败和供应商usage；本地推理与远端费用分列，价格估算标明来源与适用条件。

分别在约1000与10000条合成消息下测冷/热路径、后台构建与查询竞争、模型退出和重启。报告机器/模型/数据规模、P50/P95、峰值资源和降级比例；不得静默只扫描最近若干条以满足时延。精确向量检索无法满足可用性时，再独立评估ANN方案及过滤后漏召回，不在本批直接替换。

### 14.4 人工签收及交付

保存源码/数据/profile/策略指纹、原始失败、实际payload、冻结候选、引用位置、权限负例、恢复指纹、浏览器截图和人工签收表。公开仓库只放合成数据及脱敏汇总，不上传密钥或私人聊天。
