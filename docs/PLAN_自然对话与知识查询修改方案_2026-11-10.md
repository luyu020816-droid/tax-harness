# 自然对话与知识查询修改方案

状态：已实施基础版本，待真实模型和人工验收。基线分支 `feature_adjust_1107`，代码基线 `975aac9`。设计来源为 [连续追问 SPEC](SPEC_对话运行时与知识连续追问_2026-11-10.md)、[开源调研](意图识别开源调研_2026-11-10.md)和 [人工测试 TODO](PATCH002_TODO.md)。

当前实现用受控的回答类型处理日期、状态与功能说明。统一工具 `lookup_knowledge` 每次接受一个带 `source_type` 的 `request`，复用 `get_rules` 或 `search_knowledge` 原有结果和引用。组合需求分开调用，两条路径的结果在本轮分别校验。第 4.3 节的多来源单次调用是设计记录。

隔离库的程序冒烟已核对日期、规则追问、甲企业发票总额、统一规则入口、任务续办、发票保存与回读。该测试使用脚本化模型验证程序路径。备用本地检索模型目录的权重、profile 和选择策略已校验，真实文件入库、检索与多轮问答仍待验收。

## 1. 目标、范围和顺序

目标是在同一对话中，正确处理自然语言、上下文追问、赛事规则和用户资料。系统自动判断是否需要查知识，不要求用户输入斜杠命令。最先处理日期答非所问和规则追问失败，再接续知识检索和上下文优先保留。

比赛要求的三个业务场景必须继续可用：按企业和年月计算财税数据、经明确授权补用途或备注并回读、跨会话继续未完成任务。用户和企业权限、规则版本、写入幂等与事实依据必须保留。聊天历史与用户主动提交的知识资料分别存储、分别核权。

实施分为五批。每批完成最小基础检查后再进入下一批，完整交互、自然表述及体验验收由用户本人进行。

1. **P0 普通回答与错误分类**：修复日期、状态问题和无关检索。
2. **P0 规则追问**：上一轮规则目标用于理解，本轮查当前规则并给依据。
3. **知识依赖与自然续问**：恢复可用性，支持自动查资料与同会话代指。
4. **统一知识查询编排**：为用户提供一致的自然问答，让后端区分规则和文件来源。
5. **近期上下文与交付**：近期 5 轮优先、容量行为、基础回归和用户人工测试交接。

全量测试矩阵留作人工与后续验收参考，不作为此任务自动执行 40 轮或多模型评测的要求。已有真实缺陷需要最小回归测试，涉及写入和权限时还要做对应基础检查。

## 2. P0 普通对话：修改契约

### 2.1 问题和期望

真实轮次 `03e8c7a3-ee0f-4bb5-bbc3-ebaf4266ba72` 中，用户说「今天星期几，具体日期」，模型无依据调用聊天搜索 `query="第一张"`，最终选择 `acknowledged`，被渲染为「本轮未修改发票数据」。当前可确定错误工具调用和错误渲染，不能只凭一次轨迹断定工具描述是唯一根因。

期望新会话能正常处理日期、系统状态、系统能力和普通交流。对于日期，程序提供时区一致、可校验的宿主日期和星期。日期续问要结合原请求日期，避免跨午夜后误用新日期。

### 2.2 模块与实现

1. `backend/app/tool_schemas.py`：扩展 `AnswerBlock`，新增限定用途的普通回答块，要求类型、回答内容和必要来源明确。日期建议使用宿主渲染的结构化日期结果，时区和参考日期由宿主确定。普通文字回答必须有长度边界及明确意图使用条件。
2. `backend/app/answer_renderer.py`：为新类型添加独立渲染分支。自然表达必须服从业务事实保护：金额、发票字段、规则版本、权限、当前数据、保存状态和引用只能从已验证结果、操作回执或可信宿主状态产生。不得让新文字块为业务事实或保存成功兜底。缺少充分依据时应拒绝交付并保留可执行纠错提示。明确问题无法支持回答时允许如实说明，不能用固定「未修改发票」覆盖所有问题。
3. `backend/app/context.py`：精简并分层整理普通交流、事实依据和工具选择指令，保留必要示例与来源规则。给模型说明什么时候直接回答、何时澄清、何时调用历史或知识工具。不要靠单个关键词建立固定调度，别仅为「星期几」写一个覆盖所有场景的正则补丁。
4. `backend/app/tool_schemas.py` 的各工具 `description`：分别清晰描述适用问题、作用域、参数来源和不适用示例。`search_conversations` 查聊天记录，`search_knowledge` 查手动提交资料，`get_rules` 查正式规则；日期、普通交流不会因有这些工具就必须调用。保持现有工具名称和协议兼容，避免旧调用方失效。
5. `backend/app/runtime.py`：区分最终 JSON 校验、业务证据缺失、权限、容量和模型服务错误。返回清晰错误并保留原始 code；现有自动纠错要提示选择正确的本轮操作或重新查询，不能用自由文字掩盖失败。
6. `backend/app/answer_renderer.py` 和检查逻辑：确认回答对应用户当前需求，尤其是普通问题不能因为 `acknowledged` 有效就完成。避免在答复中添加未验证的财税数值；规则/金额相关复合问题仍要逐项交付。

**保护约束**：不能靠一个模型分类结果或几个关键词保证事实安全。任何新增自由文本均须经过明确的用途限制及后端校验。若无法可靠判断自由文字是否含受限业务断言，拒绝该交付或走已验证工具结果的安全路径，并为正常复合问题保留明确澄清。保留现有校验器和回执链路；不可仅凭“模型说普通聊天”放行。

## 3. P0 承接规则追问：本轮重新查询

### 3.1 目标路径

```text
用户：甲企业 2026 年 9 月发票用途有什么要求？
Agent：get_rules → 本轮规则结果 A → 回答。
用户：为什么？
Agent：从同会话有效上文识别 A 的对象和月份 → 本轮 get_rules → 本轮规则结果 B → 解释。
```

优先采用**本轮重新查询**，沿用 `get_rules`、`require_period`、`resolve_scope` 和当前结果证据，不修改 `_results` 使任意旧结果自动通过。历史的对象、企业、月份仅作候选，经现有用户、企业和来源校验后才能签发本轮范围。若来源不完整或有歧义，追问；如果规则变更，查询当前生效版，并在用户问历史时明确当时版本。赛事原文没有说明原因时，如实答复，不能编造。

### 3.2 修改点

- `context.py` 与工具描述：让模型知道规则追问应使用有效前文确定对象，再调用本轮 `get_rules`。错误反馈明确说明旧 `result_ref` 不能作为本轮结果，提示重新获取规则及合法范围，不能继续简单重复原编号。
- `request_evidence.py`：核对已有已确认历史、`scope_ref` 签发和到期规则，沿用当前来源链。确保模型不能凭空猜企业、月份或跨会话继承未授权范围。
- `runtime.py` 与 `answer_renderer.py`：细分 `REPLY_EVIDENCE_MISSING` 等失败类别；保留原始错误和合理重试上限。修复后「卡了吗」应根据真实状态回应，不自动重查规则或重试写入。
- 最小回归：复现原会话「用途要求 → 为什么」，验证第二轮本轮规则来源、正确版本及可读回答。另测规则在两轮间更换，确保读取新版本；原始追问重试失败要保留日志，复测独立记录。

## 4. 知识资料、自动选择及连续追问

### 4.1 先确认现有检索就绪

当前 8132 实例的 `GET /api/v1/knowledge/ready` 此前为 `ready: false`，模型目录缺 `installation.json`；`D:\tax-harness-remediation\.local\retrieval-models` 存在安装清单，但权重、哈希、当前模型目录、索引 profile 和选择策略是否一致尚未验证。

实施前在隔离环境按 [运行说明](PATCH002_KNOWLEDGE_RUNTIME.md) 逐项核验目录、权重、profile 与选择策略。优先复用已验证的本地资源，以配置方式指向有效目录，不复制或下载模型，直到确认需要。不得把演示库批量重建索引、覆盖已有文件或把查询不可用标成无匹配。规则读取在文件检索不可用时应有明确独立验证。

### 4.2 普通查询和后续指代

- 用户直接问「青枫制度普通档案能借多久」，模型应判断需要查资料，通过现有 `search_knowledge` 或第 4.3 节统一入口查询。只允许当前用户、当前授权企业中已发布有效的材料，返回真实出处。
- 后续「那能续借吗」先结合当前会话的唯一已展示资料来源作为候选，本轮重新查询当前有效版本。现有 `SearchKnowledge.document_ids` 是可选过滤条件，模型提示要求限定附件，但**当前宿主不能仅凭此承诺强制绑定**；实施时由后端核定候选和 `document_ids`，执行前及交付前复核权限、状态和版本。
- A、B 同时相关且用户说「这个」，有明确语义指向时处理相应对象，否则问「指 A 还是 B」。没有可核验的来源、目标不可访问或版本失效时说明或澄清，不伪造答案。
- 变更话题时根据本轮用户问题重新判断。知识来源可用于理解追问，不能把前次资料检索状态变成所有后续问题的持久全局模式；用户切换企业或账号后重新校验。
- 前端既有「用于对话」和附件路径要正常工作。对没有原有文件附件的聊天、旧会话和已存在资料保持兼容。聊天正文不会因此自动提交为知识资料。

### 4.3 用户视角统一的知识查询

本批先新增一个**宿主编排入口**，对模型提供明确统一的「查知识依据」能力，不迁移既有数据库，不将聊天历史加入知识资料。内部按已验证的请求目标选择或组合：

1. 正式财税规则复用 `rules.get_rules` / `resolve_in`，检查用户权限、企业、年月、主题、状态和版本，并保留规则原文与来源；用户需要判断是否必须填写时使用正式生效规则。
2. 用户文件复用 `KnowledgeRetrieval.search` 和已有引用校验；默认只检索有权访问且有效的文件，目标明确时由宿主确定允许的文档集合。
3. 结果按来源类型分别标明正式规则、上传资料、版本和定位。显式比较两者时可以并列；未知目标应澄清。用户没有限定文件时允许在有权范围内检索，不能凭空生成唯一文件 ID。
4. `get_rules` 与 `search_knowledge` 先保持兼容供已有调用和测试使用；是否将它们从模型可用列表中收敛到新入口，应在相同题集对照后决定，不能先删除破坏旧调用或写入守卫。
5. 知识索引不可用时，正式规则仍可通过原规则访问验证；涉及上传文档的部分明确标记不可用或部分完成。上传资料不能自动替换正式规则；复用 `rule_knowledge_refs` 前核对初始规则是否真的有相关引用。

统一工具建议名为 `lookup_knowledge`，请求字段为 `company_id`、`sources`（`rules`、`documents` 的非空集合）、`query`、`period`、`topics`、`document_ids` 和可选 `scope_ref`。这不是权限凭据。规则分支要求真实有效的 `period` 与 `scope_ref`，主题仅允许现有规则主题；文档分支允许按授权范围和可选文档 ID 检索。`document_ids` 未提供表示授权范围，而不是越权全库；明确绑定附件或追问对象时，宿主验证并限定 ID。若必要字段缺失，返回可追问的信息，不猜年份或企业。

响应使用一个外层结果，包含逐来源子结果 `parts[]`。每项包含来源类型、成功/不可用/未找到状态、对应的当前授权企业和版本依据；文档部分包含既有 `citation_id`，正式规则部分包含既有规则版本信息与本轮来源证据。程序必须为真实子结果记录独立来源及本轮关联，由宿主向模型提供真实子结果引用；`answer_renderer._results` 明确支持校验这些本轮子引用及其真实来源，规则卡与 `knowledge_quote` 继续使用现有权限、来源与 revision 校验。不得让模型提交自造 child ID，也不得让一个来源成功覆盖另一个来源失败。复合请求保留现有逐项完成情况。正式规则的只读查询和实际业务操作仍各自重新校验当前版本。

工具调用本身保留真实外层参数、逐分支耗时、各分支结果和失败状态。统一入口不调用或代替发票修改工具，也不改变现有资料只读约束。具体 Pydantic 字段默认值、`parts` 的状态枚举、子来源 `result_ref` 的记录方法、向旧 UI 卡片的转换以及规范化示例需在该批实现时与现有工具结果和回执代码逐字段对齐，并在实现的测试中冻结；不能将本文示意当作已有运行接口。

## 5. 最近对话与压缩

以当前一轮的上下文模型选择为基础，优先保留最近 **5 轮**已提交、可访问的用户及助手原话；旧于五轮的历史在剩余预算内按已有策略装配或摘要。不同用户、企业与删除状态继续由现有 `conversation_projection.groups` 和 `read_source` 校验。原话保护不能被模型生成的摘要替代。

实现采用 `context.py` 的历史选择处集中控制，并保留 `validate_tool_pairs`：若历史组中旧工具结果太大，可先从受保护轮的投影中安全移除完整的历史工具调用与其全部结果，保留该轮用户和已交付助手原话及必要来源；不得只丢掉一半工具配对。当前轮工具回执、强制状态、用户问题、权限及待确认写入不可裁剪。

当最近 5 轮原话加必需状态仍超出实际输入预算，不静默截断，也不假装已经记住：保留原始来源，返回明确容量原因及可执行的缩小输入提示。超长单条来源可用既有历史读取路径处理，但不能用截取片段冒充全部。核对摘要已覆盖来源的情形，避免最近原话因被摘要覆盖而无法优先提供；若需要改投影逻辑，必须验证来源权限和失效后不会重复泄露。

模型使用当前日期、规则依据和旧消息均不能绕开本轮业务校验。定量 token 指标沿用当前 `estimate_tokens` 的 UTF-8 估算，供应商实际 usage 单独展示，不把估算说成真实计费 token。

## 8. 待后续开发决定且不能跳过的细节

1. 普通文字回答的安全约束需在 P0 编码前落实为可验证接口与负例；如果现有结果校验无法可靠区分业务事实，则缩小普通回答能力并明确边界，不能未经校验放开自由业务输出。
2. 路由的基线为单 Agent 自动选择。工具描述、系统提示和回答协议的影响使用相同用例分开观察；没有实验证据前不增加独立大模型意图分类节点，也不声称描述是唯一根因。
3. 最近 5 轮是有预算前提的优先级，不保证任意长度完整塞入固定窗口。不得为了避免报错静默丢弃没有摘要或未验证的来源。
4. 统一知识入口的具体数据契约必须在动手第 4 批前补齐，且保持已有工具和规则版本兼容。不要在未验证初始化规则桥接时进行回填或重建。
5. 精准错误分类、任务保护和知识来源校验与普通回答放行是同一交付；任何一项未满足，不能标记该批完成。
