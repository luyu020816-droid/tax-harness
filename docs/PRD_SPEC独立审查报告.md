### R1 / P1：终态账本检查排在旧版本检查之后，重试不能稳定返回原结果

- 首轮定位：`C:/Users/luyu0/Desktop/赛事材料/财税连续办理助手_SPEC.md:324`、第 325 行；对应 PRD 第 120 行、AC-10、F23。当前修订位置见关闭矩阵。
- 场景：以 expected_revision=1 保存发票成功，当前 revision 变为 2，但客户端在回包前断线。完全相同请求携 revision=1 重试。
- 问题：10.1 第 2 步先检查目标 revision，第 3 步才返回已有提交账本；按此顺序会先报 VERSION_CONFLICT。若重试前又删除了任务或取消运行，旧来源/代次校验也可能把“查询既有结果”当作“执行新写入”拦下。
- 影响：原始材料要求的不重复修改、准确说明保存状态，以及本项目的稳定重试回执缺少统一实现依据。
- 建议：先核验身份、操作归属、请求指纹；找到 committed/no_change/rejected 终态后返回既有结果。只有尚未提交的操作才检查来源、运行代次和 expected_revision 并尝试写入。读取回执仍须做当前访问权限检查。
- 必需回归：提交后断线，分别在无后续变化、发票再次被改、原任务已删除时重试；均识别原操作已提交，核验状态准确，不能重新写入。

### R2 / P1：结果与版本号缺少一致读取契约，完成任务需要提交时再比较

- 首轮定位：`C:/Users/luyu0/Desktop/赛事材料/财税连续办理助手_SPEC.md:153`、第 204 行、第 252 行、第 338 行。当前修订位置见关闭矩阵。
- 场景：检查读到“缺项为零”，另一个授权动作随后清空用途并增加 data_revision；检查程序再读取最新 revision，把旧结果标成新版本。最终版本复核看不出旧数据。规则查询和 rules_epoch 分别读取也有同类风险。
- 问题：文档要求结果携带版本，但未定义明细、计数、适用规则、data_revision/rules_epoch 来自同一读取快照，也未规定任务 completed 提交时对检查版本作原子比较。版本字段本身不足以证明“当前”。
- 影响：可能发布过时缺项或错误完成任务，直接影响续办和 G5。
- 建议：规定一致读取事务或持有对应共享锁的读取协议，所有版本必须与它们所标记的内容一同产生。任务完成事务锁定相关 head，比较任务、数据、规则版本；不一致则重查。已有工具结果不得仅因本轮后续变更而重贴最新版本。
- 必需回归：在结果读取/版本读取之间，以及检查结束/完成任务提交之间，插入清空用途或规则变更，验证旧结果不能被标为当前，旧零缺项不能完成任务。

### R3 / P1：同来源只允许一个最终 patch，与含 patch hash 的去重键不闭合

- 首轮定位：`C:/Users/luyu0/Desktop/赛事材料/财税连续办理助手_SPEC.md:313`、第 319 行、第 114 行。当前修订位置见关闭矩阵。
- 场景：同一用户原话同时包含用途和备注，模型第一次只提用途 patch；恢复或下一模型步骤又给出另一 patch。两个 patch hash 不同，可以得到不同 intent_key。并发或恢复时不能仅依靠“同键去重”实现“同来源同发票只有一个最终 patch”。
- 问题：明文单一最终意图要求与持久唯一键使用的等价关系不同；没有规定何时合并、冻结同一来源的最终 patch，以及异值重放如何处理。
- 影响：开发者可能实现为多次修改，或在第一次部分写入后拒绝后续合法字段，却仍把整条请求当完成。更严重的重新解释会覆盖第一次已提交值。
- 建议：以 `(user, source, company, invoice)` 定位已接纳意图，执行前持久冻结完整 patch 与 hash；同身份异值必须冲突或转为明确的新用户指令。定义多字段请求的计划完整性，不允许恢复时重新解释已冻结 patch。
- 必需回归：同源同 patch 不同 call_id、同源不同 patch、多字段部分提案、提交后重新生成模型响应；检查账本与最终字段一致。

### 5.2 范围判断

赛事必做部分没有明显不足。当前 P0 同时包含原文修订、历史检索、上下文压缩、并发栅栏、任务删除恢复、故障演练和备份边界，明显高于原始材料允许的最小初赛实现。它们大多服务于用户额外提出的可靠记忆要求，不能仅因赛题允许简单实现就自行删去。

真正的交付风险是把全部可靠性设施、完整前端和长故障矩阵一起做完后才第一次跑通三场景。PRD 采用逐条真实链路里程碑是合适的；应先确认人员、可用开发时间和模型预算，再给工作包排期。原材料的“一周左右”不是正式截止日期，也不是当前复杂度必然能在一周完成的证据。

P1 公平对照和长对话压力评测的定位合理。向量数据库、多 Agent、同步副本留在 P2 合理，当前 40 张发票并不能证明需要这些组件。若时间紧，优先简化工作台和维护入口的外观、复用同一事件查看界面；不要削弱权限、当前数据重查、删除生效、幂等与明确偏好管理来保留展示效果。
