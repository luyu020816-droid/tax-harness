本轮结论只来自源代码、SQL约束与实际执行反例；没有用PRD、TODO、旧报告替代实现证据，也没有重新依据比赛材料判定合规或名次。采用关键性质驱动的调用链审查，不宣称逐行形式化证明全仓正确。

## 一、先回答四个问题

### 顶尖专家会额外做什么

专家会先寻找能够推翻“已完成”的例子：执行成功但没有交付；提交成功但回包失败；删掉偏好却让其他事实无法召回；来源ID完整却把关键否定词压缩掉。还会绕开自动修正测试适配器，检查原始模型协议，区分工具层正确与用户任务完成。最后明确哪些性质只能人工盲测，不能用测试数量替代。

最重要的对照不是再接一个模型，而是拿掉某道守卫后，反例是否重新出现。本轮保留修改前真实失败，作为守卫必要性的证据。

### 最原始的素材是什么

| 原始素材 | 能回答的问题 |
|---|---|
| `runtime.py`、`tools.py`、`answer_renderer.py`及实际JSON | 请求如何执行、什么条件被标记completed、如何形成最终答复 |
| migrations、实际SQL、写前/写后数据库行 | 约束是否由数据库/宿主执行，是否真实提交、重复写入 |
| sources、scope、revision、epoch、实际历史游标 | 谁说过什么、当前是否仍可用、是否串企业或重复页面 |
| compaction请求与候选摘要原文 | 来源标签是否完整；正文究竟保留了什么 |
| 进程退出点、操作账本和外部恢复指纹 | 中断后究竟回滚还是提交，恢复是否复活旧状态 |
| 测试适配器自身代码 | 测试是否替模型补过答案，从而隐藏缺陷 |

原文和数据库才是权威；模型自述、功能清单与测试总数都不能独立充当权威。

### 使用什么具体方法和工具

用`rg`沿调用链追踪；用pytest直接构造AnswerPlan和工具调用，绕过`ScriptedModel.migrate_answer`；用PostgreSQL独立读取前后值；用同一输入的红/绿对照；用真实模型三次回放验证续页；用进程终止及外部快照核对持久状态。摘要额外使用刻意丢事实的负对照。该负对照是限制证据，不是通过分数。

### 除了我们，谁能证明

任何开发者都可以在同一候选上重跑下面命令，检查断言与原始轨迹。数据库唯一键和事务提供程序可执行的约束；独立预期值、来源hash及外部快照提供可比对证据。但这些测试仍由同一团队编写，不能消除共同假设错误。第三方应在看不到实现者答案的情况下编写预期、使用新数据盲测并签收语义。最终比赛名次不能由这些证据推出。

## 二、第一性原理：系统到底要守住什么

对这个代码实现，核心价值是完成有权限、可核对、可继续的办理。三个性质必须分别成立：

1. **事实正确**：数字、用途、规则和历史引用来自实际有效来源，模型不能凭空填值。
2. **交付完整**：已经执行的查询与提交必须呈现；尚未办理的需求不能被一张正确卡片遮住。
3. **状态连续**：原文保留、正式任务/偏好有修订；删除和更正只影响真实关联，旧执行不能复活失效状态。

“存下来了”“召回找到了”“摘要没漏”“用户需求办全了”是四个不同命题。证明一个不等于证明另外三个。

## 三、代码中值得保留的深度

- [business.py](../backend/app/business.py)：金额由SQL和Decimal计算，结果不由模型生成；规则选择有企业与月份范围。
- [invoice_write.py](../backend/app/invoice_write.py)、[mutations.py](../backend/app/mutations.py)、迁移004：明确授权计划、实际revision、唯一intent、事务提交与回读核验构成完整写链路。
- [execution.py](../backend/app/execution.py)：generation、fencing token、lease和memory_epoch限制旧执行继续提交。
- [memory.py](../backend/app/memory.py)、[sources.py](../backend/app/sources.py)：原始来源、正式状态与派生索引分离；召回不是恢复正式偏好或写授权。
- [answer_renderer.py](../backend/app/answer_renderer.py)：金额、数量与回执由宿主渲染，选中的证据必须真正入模且属于当前来源。
- [recovery.py](../backend/app/recovery.py)：完整快照与独立最新回执不匹配时保持维护；不能靠换成较旧回执宣布恢复成功。

这些是实际harness价值，比工具数量、模型品牌和数据库种类更能支撑评审。

## 四、发现并修复的三处缺陷

### 1. 正确结果不等于完整交付

旧renderer逐块检查真实性，但不检查是否漏选其他已执行结果。两个实际月份都查询成功，模型只选择一个，仍能completed。已提交用途或已保存偏好，也能被无关说明替代而不展示回执。上下文组被裁掉后，执行义务更容易消失。

新增`_validate_delivery`从现有工具执行账本、operation和memory_change_ops核对当前轮。月度汇总/用途检查、当前提交回执和偏好回执缺失时，返回REPLY_EVIDENCE_MISSING，要求选择已入模结果或重新读取；不重复修改数据库。义务不随上下文裁剪消失。

**范围限制**：它证明“已执行事项没有静默漏交付”，不能证明“模型识别了用户全部子需求”。后者仍是开放设计缺口。

### 2. 续页由可选参数变成受检验的导航动作

旧实现把有效cursor放进上下文，但模型省略cursor时服务合法地执行第一页。末页也可能重新开始，工具仍成功。

新增`continuation_in`仅识别明确的续页控制短语，绑定当前会话最后实际展示的页面。漏传/替换cursor返回HISTORY_CONTINUATION_REQUIRED及核验后的完整参数；最终答复须包含真正的续页结果。导航因记忆或范围变化失效时明确停止。引号、否定、新日期及新企业不会被强行接上旧范围。

这是一段有限导航语法，不是通用意图理解。其他未覆盖表达仍需盲测，不能宣布任意说法都不会翻错。

### 3. 删除偏好误伤无关业务历史

旧`suppress_old_history`除了处理来源和依赖，还会抑制所有包含旧偏好值的早期消息。独立库复现：删掉甲企业“简洁”偏好，乙企业“项目名称为简洁办公”的业务原话也变为suppressed。原文未丢，但普通召回不可用。

移除文字子串批量失效，保留真实来源ID及上下文依赖的失效处理。同一反例修复后保持active，实际日期召回可找到；旧偏好来源仍suppressed。没有新增模型、索引、表或依赖。

已有历史误伤记录不能自动全量恢复：suppressed也可能代表真实删除，必须逐来源审计。同一原话包含多个事实时，当前仍存在来源级保守屏蔽；其他正式偏好可保留，不等于原话可逐事实召回。

## 五、仍不能给高评价的部分

### 未执行子需求没有程序级完成判据

`request_evidence.prepare_frame`只提供企业、月份与scope，并不形成完整且可核验的子需求清单。`tasks`对每用户/企业只保留一个未完成槽。模型完全没识别的子需求不会进入工具账本，本轮交付守卫也无从发现。

下一步应先为已有组合场景明确“所问事项→需要的结果/必要追问→未完成状态”，不先上多Agent或通用规划平台。需要用户原句、独立预期和未公开问法测试；仅再加一句prompt不足以关闭。

### 摘要标签完整不等于语义完整

负对照向真实compact提交来源标签齐全、但没有柜号和“不得外发”的摘要，程序仍发布，原文保持完整。当前`_decode`和compact能验证格式、来源集合、修订和epoch，不能证明事实全部保留。不要称为无损压缩或零遗漏记忆。

正式状态仍应来自任务/偏好数据库，具体历史事实仍需读取原文。若提高摘要质量，应评估否定、更正、例外等原子事实保留率，不能用covered_sources覆盖率替代。

### 知识模块主要交付依据，不保证直接回答

`_knowledge_quotes`主要生成来源说明和原文卡片，FinalReply没有自由事实结论字段。这有利于避免编造，但“找到相关条款”与“明确回答是否允许、为什么”不是同一个体验。需要逐问题盲评，不应仅凭召回分数称知识问答成熟。

### 原生推理根因和真实输入质量仍未证明

隔离进程和有限重试可以控制影响；三轮没有重启不能证明内核崩溃根因已修。OCR置信分数也不是原件正确率。只凭代码不能给任意扫描件、任意历史表达和任意长对话作零错误保证。

### 错误修复可能放大为无效执行——本轮保留的新失败

最终真实模型40例有1例失败：L08-02“去年我说过的发票用途都是什么？”首次search_history已成功返回not_found，且给出允许的history_not_found/history_insufficient说明码。模型却选择result(view=history_page)，而实际模式是lexical_only；原有视图守卫正确拒绝。

当前修复反馈只说明“整页只能使用日期结果”，没有明确建议保留成功检索、直接使用对应说明码。模型于是改查一整年，被31天窗口限制拒绝后又一次请求6段日期窗口。工具组与必需状态超出16000输入预算，本轮以CONTEXT_CAPACITY_EXCEEDED失败。

这不是原文物理丢失，也不是本轮续页cursor错误。可确认的是：错误恢复缺少足够具体的纠错提示，并可能导致不必要的查询扩张；不能从一次轨迹断言所有因果或已稳定复现。下一步应冻结该错误轨迹，验证“选择错误视图→返回可行答复选项→无需额外查询结束”的原始协议反例，再做定向重复。当前保持开放，不增加预算、不修改原断言、不用成功重跑覆盖这次失败。

## 七、评委判断

这套代码已经展示了有价值的受控办理能力，尤其是授权、幂等、状态修订和来源核验，值得进入现场复核。但我不会仅凭当前实现认定达到特等奖成熟度：最薄弱的环节是完整需求闭环与记忆语义验证，而非功能数量。

本轮优化只收紧交付和导航协议，并删除一段会误伤历史的逻辑。下一阶段应使用陌生组合需求与独立预期检验“少办、错记、假完成”，保留失败，不扩大功能清单。比赛合规、复赛资格和奖项仍需实际材料与评审，不能从代码单独推出。
