2026-11-20 · 面向开发负责人和独立验收人

**建议保留现有 PostgreSQL、来源记录和操作日志，先改三条规则：同一件事如何认定为同一对象，一次更正影响哪些对象，每轮请求有理由读取哪些内容。** 当前系统已经有原文、任务、偏好、知识版本、摘要、历史索引和审计快照。它能记住信息，但在信息发生变化时，有时同时保留两个互相矛盾的值，有时又把完全无关的历史排除掉。扩大模型窗口或再加一层向量检索，都无法解决这两种现象。

## 一条业务请求需要几种记忆

假设用户说“以后甲企业月报用表格。九月发票先等财务复核，今天只改 F002 的备注。”这句话可以只存一份原文，但会产生三种寿命不同的记录。月报格式可以跨会话使用，“等财务复核”要随任务持续到解决，改备注的授权只针对本次指定操作。即使三者来自同一句话，删除格式偏好也不该撤销待办，摘要更不能把旧授权带到下个月。

| 哪个问题要有唯一可信的回答 | 谁负责记录 | 何时读、何时失效 |
|---|---|---|
| 用户当时到底说了什么 | 原消息、说话角色、来源版本及可定位的原句 | 查历史或核对歧义时按当前权限读取。用户原话可以证明当时的意图，今天再次执行仍需当前授权 |
| 今天哪些事还没办，允许改哪几张票 | 任务、具体待办、确认计划及发票操作记录 | 优先读取当前状态，局部更正精确到对象或字段。重试按原操作号核实结果 |
| 这个人或这家企业今后有什么要求 | 明确保存的偏好、适用企业、事项、版本和来源 | 在相应场景使用。个人默认、企业限定和本次例外各有范围，更正能找到同一条要求 |
| 哪条制度、哪个月的金额有效 | 已发布的知识版本、有效期、原文件及业务表 | 按企业、查询时点和数据版本读取。助手过去说过的金额只可解释历史 |
| 之前谈到哪里、从哪里找原文 | 近期对话、摘要、关键词或语义索引 | 只承担导航和压缩。候选命中后重新核对来源、权限和有效性 |
| 当时模型看到了什么，系统做了什么 | 实际模型输入清单、工具记录及操作回执 | 用于审计和恢复。历史输入快照、模型服务商前缀缓存命中率均不承担有效偏好或授权的判定 |

已有实现值得保留。偏好有修订与删除记录，任务可以核对业务数据和规则版本，历史原文按角色读取，摘要记录覆盖来源，历史索引 worker 有租约和发布前校验，实际模型输入也有快照。前次专项还验证过制度停用后，旧摘要会退出有效输入。这些机制为下面的改动提供了基础。[来源读取](../backend/app/conversation_log.py) · [索引作业](../backend/app/conversation_jobs.py) · [上下文校验](../backend/app/context.py) · [已有验收](./复赛第4_5_7项_验收报告_20261119.md)

## 七个可独立核对的架构问题

优先级按后果排列。P0 表示会静默改变用户已托付的事项，P1 表示状态冲突、正常办理中断或输入退化。第 7 项单列为产品能力边界，由实际待办场景决定改动幅度。

| 编号 | 输入或操作 | 实际观察 | 独立复验应看到什么 |
|---|---|---|---|
| AR-01 · P0 · 局部更正覆盖待办 | 在任务服务建立九月查询，要求保留“税额、含税金额”两列，待财务复核。随后只提交月份改成十月，省略待办字段 | 同一任务的月份更新成功，`unresolved_json` 从包含两列及复核待办变成 `{}`。旧修订仍可查，但当前办理状态已丢失 | 用户设置的展示要求及待办保留。九月专属的计算结果单独标为待刷新。明确清空字段与省略字段有不同语义 |
| AR-02 · P1 · 同一偏好有两个名字 | 跨会话先说“今后回复要简短”，再说“更正刚才的要求，今后回复要详细”。受控模型两次走保存，分别给出合法键 `response_length`、`answer_length`，值都忠实于原话 | 新会话的实际模型输入同时含“详细”和“简短”，二者都在正式偏好列表里。冲突发生在识别更正对象时 | 能识别唯一旧对象时产生新修订，旧值退出有效输入。确有多个候选时询问用户。增加对照，“正文简短、附录详细”可以同时有效 |
| AR-03 · P1 · 改月报格式使无关历史消失 | 先给甲企业设置月报用项目符号，问“一周有几天”，实际回答“一周有七天”。再把月报格式改成表格 | 更改前该轮出现在同会话的历史投影中，更改后整轮被排除，原因为 `SOURCE_INVALIDATED`。测到的是后续输入使用的历史投影，原始数据库记录仍在 | 更正后仍可以接着追问七天的回答。确实使用旧格式偏好的派生内容按其用途失效。无法区分时可返回仍获授权的用户原话和待核对标记 |
| AR-04 · P1 · 甲企业写入打断乙企业读取 | 同一用户在乙企业发起“一周有几天”，worker 领取后、调用模型前，在甲企业保存“总账表头用全称” | 乙的请求变为 `interrupted / STALE_CONTEXT`，模型调用次数为 0。新开一轮重复乙的问题可以完成 | 乙的原请求正常完成。若改变乙请求实际依赖的偏好，重新装配读取结果。撤权和授权范围缩小依然立即生效 |
| AR-05 · P1 · 新会话也能被不相关记忆挤满 | 相同 Agent、工具和 16,000 输入预算，在乙企业新会话输入同一个日常问题。保留两条原有偏好作基线，再增加 20 条只用于不同年度附表的说明 | 基线估算 14,920，可组装。增加后估算 28,061，报 `CONTEXT_CAPACITY_EXCEEDED`，历史预算占用为 0。此数为本地估算器结果 | 同一预算下普通问题能回答，并且不会注入这 20 份附表说明。明确办理其中一张附表时能找到对应要求；对于适用的强制限制，容量不足要显式处理 |
| AR-06 · P1 · 跨会话历史的产品承诺不一致 | 核对同一份实际系统提示，再调用正式回复渲染函数 | 提示一处要求跨会话用独立历史工具，另一处要求不搜索并输出 `conversation_boundary`。组装器写入 `independent_history_tools`，渲染器在这个状态下返回 `REPLY_EVIDENCE_MISSING`；`disabled` 对照能正确生成边界说明。渲染结果已实测，真实模型选择哪条指令仍待验证 | 在“没有问历史、明确查本人历史、当前 Agent 禁用历史”三种场景，工具集合、系统指令、实际行为和用户回复一致 |
| AR-07 · 能力边界 · 每人每企业一个活动任务槽 | 同一用户在甲企业保留一项月度查询，再另开该企业同月的一项规则解释任务 | 第二次创建返回 `NEEDS_CLARIFICATION`，询问是否替换第一项。原任务保住了，但两件事不能作为两个独立进行中的任务保存 | 先用赛事场景验证需求。至少能在关闭会话、重启、局部取消后清楚列出剩余事项。若一个任务下的独立待办已能满足，就沿用该结构；确需独立生命周期时再扩为多个任务 |

**定位。** AR-01、07 可从任务更新和任务槽开始，尤其注意输入模型将缺省的 `unresolved` 设为 `{}`。AR-02 的数据库唯一约束是用户、作用域和字符串键，读取时也以该键合并。AR-03 的装配清单把整批正式状态写入依赖，更正会抑制引用该对象的先前轮次来源。AR-04 的记忆版本号和摘要失效 SQL 均按用户生效。AR-05 的所有有效偏好都进入必要系统消息。AR-06 可直接对照系统提示第 40、58 行和渲染函数第 958 行。[任务](../backend/app/tasks.py) · [工具输入定义](../backend/app/tool_schemas.py) · [记忆读取](../backend/app/memory.py) · [记忆变更](../backend/app/memory_changes.py) · [历史投影](../backend/app/conversation_projection.py) · [运行守卫](../backend/app/execution.py) · [输入组装](../backend/app/context.py) · [回复渲染](../backend/app/answer_renderer.py)

**与前次报告的关系。** AR-01 的用户确实授权了修改，错误在于写入范围过大，和 TURN-01 的误取消不同。AR-02 两次保存的值都忠实于当时原话，补足了 MEM-01 的“同一对象”问题。AR-05 在历史长度为零时即可复现，单独修复 CTX-01 的最近五轮压缩仍不足以解决它。AR-03、04 反映出一个共同后果：当前系统对无关变更也会丢掉原本可用的信息或中断工作。

## 建议的改动顺序

### 第一步：定义哪些事实能够被改，以及一次能改多少

- [ ] **先修任务更新的语义。** 将用户提出的待办、展示约束与计算生成的缺项分开。更新请求只覆盖明确提供的字段。月份改变时重新检查依赖月份的计算结果。以 AR-01 为通过条件，同时回归前次 TURN-01 的取消保护。
- [ ] **再给偏好一个稳定身份。** 对已有高频要求先从回答详略、金额格式、排序等少数维度开始，保留自定义项。保存时结合主体、企业、适用事项和具体维度定位旧记录，明确区分“新增”和“更正”。旧数据中已有两条冲突记录时保留历史并要求消歧，不能因为名称相似就自动合并。以 AR-02、原 MEM-01/02 及其正例为通过条件。

### 第二步：把“允许读取”“与本轮相关”“历史回答实际依赖”分开处理

- [ ] **让宿主分两次做决定。** 先执行用户、企业、Agent 和来源权限检查，再选择与本轮相关的任务、限制、偏好和摘要。适用的禁止项、待确认操作状态由宿主确定并保留；篇幅大的低相关格式模板按需读取。先用现有字段和明确业务意图实现，再根据遗漏样例决定是否需要新的检索手段。
- [ ] **把存在于输入中的对象与影响有效性的对象分别记录。** 审计清单完整保留实际发送内容。任务依赖原操作和业务版本，制度结论依赖引用版本，历史原话记录当时发生的事实。无法判定一段自由文本是否受旧事实影响时，保守处理该段；可重新组装仍可访问的材料。严禁仅凭模型声称“没用到”就放宽权限。
- [ ] **缩小普通更正的失效范围。** 个人规则、企业规则和具体对象修订各自可辨。读取阶段可在相关变化时重装一次，写入阶段按目标版本、授权和操作编号复核。全局撤权或账号停用继续有全局效力。先让 AR-03、04、05 通过，再验同企业冲突、撤权与旧 worker 迟到提交。沿用当前事务与版本设施即可开始。

### 第三步：统一原入口的读取策略和恢复行为

- [ ] **为跨会话历史选择清晰的默认行为。** 建议普通对话只自动恢复正式任务和明确保存的偏好。用户明确要求查本人历史时，依据当前 Agent 权限、企业与来源检索，标明日期和角色。权限或产品设置禁止时，工具和回复都给出同一种边界。以 AR-06 的三组用例验收。
- [ ] **用同一业务故事决定是否扩展任务模型。** 先保留 A、B 两个待办，更正 A 的月份，取消 B，切企业再回来，重启后仅继续 A。要求原入口、任务状态、操作日志和模型输入能共同解释每一步。仅在单个任务下的独立待办无法表达时拆成多任务。参见 AR-07 和前次 REC-01。

## 整体验收标准

在统一提交上准备两家企业、两个用户和职责不同的两个 Agent，固定同一模型、预算和测试材料，修复前后重跑同一组输入。每次同时留存回答、实际模型输入、来源及修订、业务对象和操作状态。验收至少核对四项结果：

1. **局部变更正确。** 显式修改的对象符合预期，无关待办、会话和授权记录保持其应有状态。一次性要求到达本轮结束时失效。
2. **该忘的和该记的都测。** 更正、删除、停用或撤权后，旧值进入有效回答的次数应为零。另设明确应保留的对照，包括同一消息里的第二项偏好、无关历史和另一企业的进行中请求。
3. **同一事实有可说明的优先级。** 原文回答“过去说过什么”，当前任务和业务表回答“现在是什么状态”，操作日志回答“是否真的保存”。三者冲突时，答复显示证据及其适用时点。
4. **控制成本也控制遗漏。** 分别记录新会话、五轮长对话、报告任务的输入估算和模型实际用量，检查强制约束召回、无关模板入模数、普通请求中断数。分别测依赖服务可用、索引尚未就绪和重启，避免把一次成功演示当成完整验收。
