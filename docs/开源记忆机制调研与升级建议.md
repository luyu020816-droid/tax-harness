# 开源记忆机制调研与升级建议

调研日期：2026-10-25（Asia/Shanghai）。

本报告记录 DeerFlow、LangGraph、Mem0、Letta/MemGPT、OpenViking、Graphiti 六类项目的官方文档与源码证据，供财税连续办理助手的记忆设计使用。以下代码链接主要指向调研时的 `main` 动态分支，未形成统一的固定提交快照；后续直接复用代码前需要另行锁定提交。未运行模型付费 API、统一性能/准确率对照或第三方项目测试，未对本地 RSI 项目做修改。Stars 为访问时 GitHub 页面显示的近似快照，抓取时间可能不同，不能作为实时排名、质量或比赛适配性的证明。

**建议先借 DeerFlow 的记忆写入治理和压缩前捕获、LangGraph 的会话状态与跨会话存储分离、Letta 的常驻与按需记忆分层。Mem0 适合作为偏好检索和接口设计的对照；OpenViking 的分层读取适合后续大量资料，Graphiti 的来源与时间有效性可以借入关系表。初赛不同时接入多个记忆运行时。**

在本项目中，记忆与上下文管理可以作为核心技术特色，完整 Harness 仍包括工具执行、任务状态与真实结果反馈。企业规则和当前业务数据有独立权威来源，不并入模型可以自由改写的长期记忆。

## 二、Mem0：借鉴记忆条目化、写入去重和检索可解释性

### 2.1 实际机制

当前 `Memory.add(infer=True)` 的核心路径是：读取同范围的最近消息，检索已有记忆，调用模型抽取新事实，再进行批量向量化与 hash 去重，最后追加存储。显式 `update`、`delete` 和 `history` 接口仍然存在。自动抽取不能等同于偏好更正已经使旧值失效。[核心路径 main.py：`_add_to_vector_store`](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py#L839)

当前 `ADDITIVE_EXTRACTION_PROMPT` 明确为 ADD-only，并允许从用户与助手消息提取内容，还包含从问题中推断隐含偏好的指令。它要求区分用户陈述与助手建议的归属。对本比赛，建议保留归属区分，改成只把用户明确表达的偏好作为有效偏好；助手建议、临时意图与推测应留在各自的记录类型里。[抽取提示词源码](https://github.com/mem0ai/mem0/blob/main/mem0/configs/prompts.py#L414)

历史存储保存每条记忆的旧值、新值、操作事件、时间与删除标记，也单独保存消息。这个机制适合展示偏好的变化，但默认 history 表没有直接表示“该记忆来自哪个消息 ID、哪个工具结果”的完整字段；比赛版本应增加来源关联。[SQLite history / messages 模型](https://github.com/mem0ai/mem0/blob/main/mem0/memory/storage.py#L92)

检索评分提供可选的解释信息，组合语义分数、BM25 分数与实体加分。其阈值先约束语义分数，之后才组合其他分数。核对主路径可见，候选以向量结果为基础，关键词结果给候选加分；纯关键词命中而未进入向量候选的记录，不会自动进入最终集合。因此，不能把它理解为任意语义漏召回都能被关键词分支补上。[评分实现](https://github.com/mem0ai/mem0/blob/main/mem0/utils/scoring.py#L55)、[检索候选构造](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py#L1495)

### 2.2 隔离与更新的适配边界

Mem0 开源库提供 `user_id`、`agent_id`、`run_id` 与元数据过滤，当前代码防止自由元数据改变内置身份字段。源码中的自动写入预检索只选择三个内置身份字段，`company_id` 自定义元数据不会进入该步骤。应由服务端构造包含用户和企业的范围，不能只在对外搜索时补一个企业过滤。`get/update/delete(memory_id)` 路径也需要业务服务复核归属。[范围构造与身份保护](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py#L126)

对“以后默认按月展示”改成“改为按季度展示”，我们建议按稳定偏好键更新当前值、保留旧版本和来源，并使所有召回路径排除旧值。对“忘掉这个偏好”，还需防止历史消息被再次抽取后使它复活。这是比赛版本需要补充的产品语义，不能认为单次删除向量即已满足。

### 2.3 开源与云端能力必须分开

官方当前对照页确认：开源具备基础 CRUD、单条历史、实体范围、有效期、重排和自定义抽取；云端才提供组织/项目与 `app_id`、项目事件流、图记忆、衰减、时间推理与 Dream 后台整合等。当前 V3 开源已移除旧外接图存储集成。不要把云端的自动过时处理与后台整合当成安装开源包就能使用的能力。[官方 Platform vs OSS](https://docs.mem0.ai/platform/platform-vs-oss)

官方 OSS 概述允许库式集成或自托管服务，模型、向量存储与重排器可配置；自托管并不代表模型和 embedding 没有费用。文档中关于 dashboard 的页面表述存在差异，若后续需要界面能力，应以锁定提交的 `server/` 实现为准。[官方开源概述](https://docs.mem0.ai/open-source/overview)

### 2.4 对本项目的取舍

| 值得模仿 | 需要升级或限制 |
|---|---|
| 每条记忆独立 ID、去重、独立历史 | 稳定偏好键、修订号、来源消息 ID 与显式失效状态 |
| 抽取前参考少量最近消息与已有记忆 | 明确偏好才生效；助手输出保留建议属性 |
| 检索分数可解释，便于发现召回问题 | 业务编号采用精确分支；不能只让关键词给向量候选加分 |
| 身份范围与自由元数据分离 | 用户和企业范围由服务端绑定，不能由模型自由填写 |

**判断：适合作为偏好记忆的设计参考。可以选择性借代码，不建议让它直接承担任务状态和财税规则的最终事实存储。** 本比赛最先需要的是明确更新语义、严格归属和来源可查，泛化自动抽取可以后置。

## 三、Letta / MemGPT：借鉴常驻记忆与按需读取的分层

### 3.1 先分清旧机制与当前运行时

官方 V1 文档仍保留 memory blocks、archival memory 和 conversation search：memory blocks 直接留在上下文，归档内容通过工具按需查询，conversation search 查询过去原始消息。V1 已在文档导航中标成 legacy，不能将这些 SDK API 当成当前新 SDK 的相同接口。[V1 归档记忆文档](https://docs.letta.com/v1-sdk/memory/archival-memory)、[当前源码迁移说明](https://github.com/letta-ai/letta)

V1 blocks 带描述、长度限制与只读属性，可共享给多个 agent。文档还明确：直接设置 `value` 是完整替换，多个写入者并发时后写会覆盖先写。可借鉴块职责与只读规则，但业务任务和偏好的更新应加入版本条件，避免覆盖。[V1 memory blocks 文档](https://docs.letta.com/v1-sdk/memory/memory-blocks)

当前 Letta 使用 MemFS：记忆是 agent 的 Git 仓库，通过文件系统投射到运行环境。核心记忆常驻上下文，深层资料通过目录索引按需读取；默认没有向量索引，可另外安装搜索 mod。它说明“长期记忆”并不天然等于向量数据库。[当前 MemFS 官方文档](https://docs.letta.com/concepts/memfs)

### 3.2 已读源码与对应机制

| 已读路径 | 可核验行为 | 对比赛的启发 |
|---|---|---|
| [`memory-format.ts`](https://github.com/letta-ai/letta-code/blob/main/src/agent/memory-format.ts) | 区分 MemFS v1/v2；v1 的 `system/` 与 v2 根 Markdown 被识别为核心记忆；深层文件通过目录 `MEMORY.md` 标记决定投射 | 给当前任务与必要偏好固定输入位置，深层证据按需取 |
| [`memory-constraints.ts`](https://github.com/letta-ai/letta-code/blob/main/src/agent/memory-constraints.ts) | 提交前校验单文件、核心总长度、目录深度与只读文件；限制配置本身也受保护 | 输入预算与规则只读通过程序约束，不能只写在提示词里 |
| [`memory.ts`](https://github.com/letta-ai/letta-code/blob/main/src/agent/memory.ts) | 普通非 MemFS agent 的默认块为 persona/human；块可带描述与只读标志 | 记忆要声明职责和写入权限，避免一个“大摘要”承载全部内容 |
| [`memory-confinement.ts`](https://github.com/letta-ai/letta-code/blob/main/src/memory-confinement.ts) | 后台记忆进程的文件系统范围限制；不能读写其他 agent 的记忆，无支持的沙箱时拒绝降级运行 | 隔离需要执行层保证，不能让召回提示词充当权限边界 |

当前两个文档对核心路径的表述有版本差别：新 MemFS 概念页说明根 Markdown、旧布局使用 `system/`；SDK Memory 页仍展示 `system/`。`memory-format.ts` 明确兼容两种布局，因此应记录为布局演进，而不是混写成一套固定目录要求。[MemFS 文档](https://docs.letta.com/concepts/memfs)、[SDK Memory 文档](https://docs.letta.com/agent-sdk/memory)、[布局检测源码](https://github.com/letta-ai/letta-code/blob/main/src/agent/memory-format.ts)

### 3.3 开源、托管与不适配点

当前源码公开且仓库标示 Apache-2.0。SDK 文档将 Letta 托管的共享 memory repositories 标为云端能力；自托管环境可用自己的 Git remote 实现共享。文档还提供 Dreaming 后台整合，但其存在不等于财税偏好经过了用户明确确认。[Letta Code 仓库](https://github.com/letta-ai/letta-code)、[SDK Memory / shared repositories / Dreaming](https://docs.letta.com/agent-sdk/memory)

我们的业务是按用户与企业隔离，Letta 的 agent 归属和共享机制需要再映射；共享记忆本身不是权限系统。用 Git 管理规则来源与变更记录有价值，但每次修改财税任务状态都走 agent 编辑文件和 Git 提交，会增加同步和一致性成本。本赛题可用数据库记录当前状态，借其“少量常驻、其余按需”的思想。

**判断：最值得模仿上下文分层与程序预算约束。首版不建议引入整套 Letta，也不建议让模型自由改写承载任务事实的 Markdown。** 当前任务、明确偏好和适用规则可形成小而固定的工作区；原文历史与证明材料放在可检索的证据层。

## 四、Graphiti：借鉴来源关联与时间有效性，保留未来图检索选项

### 4.1 事实与来源是可关联的

Graphiti 的实体事实边保存 `episodes` 来源列表，以及 `created_at`、`expired_at`、`valid_at`、`invalid_at`。前两者描述系统何时记录或失效，后两者描述事实何时成立或结束。源码还保留 `reference_time` 以解释原文中的相对日期。这种区分适合处理“今天获知某规则上月生效”等情况。[EntityEdge 源码](https://github.com/getzep/graphiti/blob/main/graphiti_core/edges.py#L242)

消息、文本和 JSON 可以作为 episode。保留原始来源，再抽取实体与关系，使得“从哪里得出这个事实”有可回查的入口。[EpisodeType / 节点源码](https://github.com/getzep/graphiti/blob/main/graphiti_core/nodes.py#L49)

冲突处理会结合新旧事实的有效时间，把旧事实的 `invalid_at` 和系统失效时间设定下来。候选冲突识别与事实抽取依赖模型，不能理解为确定性业务规则引擎。对本项目应借时间字段与新旧版本关系，规则适用仍由程序显式筛选。[事实解析与失效源码](https://github.com/getzep/graphiti/blob/main/graphiti_core/utils/maintenance/edge_operations.py#L664)

### 4.2 混合召回由配置选择

官方配方包含 BM25、向量相似度，部分配方还加入 BFS 图遍历；结果可用 RRF、MMR、节点距离、来源提及次数或 cross encoder 排序。实际使用哪些方法由选定配置决定，并非每个搜索默认运行所有分支。`SearchFilters` 支持有效时间、失效时间、创建时间与属性条件。[检索配方源码](https://github.com/getzep/graphiti/blob/main/graphiti_core/search/search_config_recipes.py)、[搜索过滤源码](https://github.com/getzep/graphiti/blob/main/graphiti_core/search/search_filters.py)

### 4.3 删除需要处理派生内容

当前 `remove_episode` 不只删除原文：还删除唯一依赖该来源的边，保留其他来源仍支持的边，移除不再有支持的节点，并重建幸存节点摘要。重建摘要失败会记录异常且保留旧摘要，因此不能把该接口视为所有错误情况下都已完成不可恢复遗忘的承诺。[删除来源及重建摘要源码](https://github.com/getzep/graphiti/blob/main/graphiti_core/graphiti.py#L2002)

这直接启发我们的删除设计：用户删除某项偏好后，当前值、索引、历史摘要与后续抽取都应尊重失效标记；仅删除一条数据库或向量记录，不足以保证旧值不会被摘要带回。业务审计记录是否保留，应与“可供模型召回的有效记忆”分清。

### 4.4 隔离、托管边界与成本

`group_id` 是图分区，`search` 接受可选 `group_ids`；它提供的是范围参数，需要应用在读取、按 UUID 修改和删除时执行授权。官方 README 明确 Graphiti 需自备图数据库、LLM、embedder，并自行建设用户、线程、接入、访问控制与运维；Zep 的托管组织、服务与运营能力不能归到 Graphiti 开源包里。[Graphiti 搜索接口](https://github.com/getzep/graphiti/blob/main/graphiti_core/graphiti.py#L1761)、[官方 Graphiti 与 Zep 对照](https://github.com/getzep/graphiti#graphiti-and-zep)

图数据库与多次模型抽取会扩大部署、延迟和故障面。对于少量企业规则、明确偏好和结构化待办，我们可以直接以关系表保存来源及时间版本；多实体、多关系、跨资料关联成为真实需求后，再评估图检索。

**判断：最值得模仿“事实有来源、旧值有生效区间、删除要清派生结果”。初赛不建议为了记忆引入完整知识图谱。**

## 五、三个项目的可移植机制对照

以下为结合比赛场景的工程判断，不是各项目官方的优劣排名。

| 我们的问题 | 主要参考 | 首版适配方式 |
|---|---|---|
| 明确偏好如何持久化 | Mem0 条目与历史；Letta 常驻核心记忆 | 按稳定偏好键保存当前版本，附用户原话来源 |
| 任务怎么续办 | Letta 小型工作区的思想 | 结构化任务同步落库，恢复后重查业务数据；不靠相似搜索找唯一待办 |
| 本轮只给模型必要信息 | Letta 分层与预算约束 | 当前任务、当前偏好、适用规则固定位置；历史按需检索 |
| 用户更正如何立即生效 | Mem0 显式 CRUD；Graphiti 时间与来源 | 创建新版本并使旧值失效，过滤所有旧摘要和索引 |
| 删除后不再被历史带回 | Graphiti 来源删除与摘要重建 | 保存删除/失效标记，校验派生摘要来源；不能把原始对话重新抽成有效偏好 |
| 用户、企业隔离 | Mem0 身份范围；Graphiti 分区参数 | 服务端绑定范围，检索前过滤，按 ID 更新和删除也复核归属 |
| 语义同义表达怎样找 | Mem0 可解释评分；Graphiti 混合配方 | 精确业务字段先查；历史证据按需加关键词与向量，记录各分支命中原因 |
| 答案如何可核对 | Mem0 变更历史；Graphiti episode 关联 | 记忆 ID、版本、来源消息、工具结果与本轮输入可关联 |

总体建议：把成熟项目的机制移植成小而清楚的本地记忆模块，而不是一开始替换掉现有 Harness。最有比赛价值的升级顺序是来源与隔离、偏好更新删除、可靠任务续办、输入分层与预算，最后依据真实漏召回案例增加向量检索。

## 六、DeerFlow：最优先借鉴写入治理和上下文压缩的接续

DeerFlow 是完整 Harness，记忆是其中一个运行模块。当前官方说明中默认本地实现为 DeerMem，另有 Mem0、Honcho、OpenViking 等可选后端；一个可选后端的能力不能推定为所有后端的共同能力。[官方记忆说明](https://github.com/bytedance/deer-flow/blob/main/frontend/src/content/en/harness/memory.mdx)

### 6.1 长期事实先判断范围与用途

已读 DeerMem updater 中的 `_fact_scope_gate_reason`：自动抽取条目必须具备 scope、durability、authority 标签，接受 user / durable / descriptive，缺失或不符合即拒绝；摘要和删除也有对应筛选。模型先提取和分类，程序再验证允许的分类，不能据此宣称程序独立证明了语义正确。[updater.py 源码](https://github.com/bytedance/deer-flow/blob/main/backend/packages/harness/deerflow/agents/memory/backends/deermem/deermem/core/updater.py)

这适合防止把“本次只处理甲企业”“这次先改这一张”“不用再确认这次操作”等临时上下文升级为长期用户偏好。我们的偏好写入还应增加赛事要求的明确表达校验与来源原话；模型置信度高不能替代用户明确表达。公司/任务范围另有结构化任务状态，不因被拒写长期偏好而丢失。

### 6.2 更正不能变成只删除旧值

同一 updater 的替换流程在新事实通过筛选、去重与容量控制后，才允许对应旧事实删除；新值未落地时不退化成只删旧值。它也对整合来源的存在性和候选资格进行检查。可借这个不变量，将我们的同键偏好更正做成一次受版本约束的原子变更。[事实替换与整合实现](https://raw.githubusercontent.com/bytedance/deer-flow/main/backend/packages/harness/deerflow/agents/memory/backends/deermem/deermem/core/updater.py)

该实现中的语义标签和冲突识别仍由模型提出，不等于财税规则或用户授权的确定性判断；企业规则由维护入口管理，一次性写授权依赖本轮真实指令。

### 6.3 捕获身份、异步整理与压缩钩子

`MemoryMiddleware` 在入队时从运行上下文捕获 user_id、thread_id 和 trace_id，再把消息交给记忆后端。这个做法避免后台线程丢失当前用户身份。消息筛选和抽取属于后端实现，默认描述的是用户消息与最终助手回复的捕获。[MemoryMiddleware 源码](https://github.com/bytedance/deer-flow/blob/main/backend/packages/harness/deerflow/agents/middlewares/memory_middleware.py)

`DeerFlowSummarizationMiddleware` 提供压缩前钩子，携带即将移除与保留的消息，结果结构还可以携带任务历史。它将“丢掉对话文本之前保留必要信息”变成明确的生命周期环节。[summarization_middleware.py 源码](https://github.com/bytedance/deer-flow/blob/main/backend/packages/harness/deerflow/agents/middlewares/summarization_middleware.py)

对比赛的适配：已保存业务结果与当前任务必须在回复/压缩前可靠持久化；重要偏好更正与删除成功应在确认持久化后才告知用户。低影响的历史整理可异步批量处理。异步入队不等于已持久保存，不能把后台归纳充当任务唯一副本。

### 6.4 后端契约、检索和限制

`MemoryManager` 将写入、上下文读取与后端工厂分开，可选搜索和管理能力显式声明；某后端不支持的操作需返回不支持。适合借鉴统一调用和错误语义，但比赛已要求查看、更正、删除，这些不能因为后端可选而从产品中消失。[MemoryManager 源码](https://github.com/bytedance/deer-flow/blob/main/backend/packages/harness/deerflow/agents/memory/manager.py)

DeerFlow 官方当前说明提供本地全文检索、可选中文分词、按范围管理与预算注入，并区分自动中间件和模型工具模式。对我们的启发是先把必需任务与偏好装配正确，再根据问题检索历史；不直接移植其全局摘要策略。部分文档仍含旧文件布局，源码、raw 与文档页面抓取也可能不是同一个提交，应锁版本复核后再迁入代码。[官方记忆文档](https://github.com/bytedance/deer-flow/blob/main/frontend/src/content/en/harness/memory.mdx)、[项目 README 的记忆说明](https://github.com/bytedance/deer-flow#long-term-memory)

**判断：在六类候选中最值得优先读和借其运行机制。应适配到用户＋企业范围、明确偏好和权威业务结果，初赛无需迁入完整 DeerFlow、沙箱和子 Agent。**

## 七、LangGraph：优先借状态与长期存储的职责分离

官方将短期记忆定义为 thread 状态，由 checkpointer 持久化；长期记忆由跨 thread 的 Store 保存，使用自定义 namespace。它提供的是明确的持久化和隔离组织方式，记什么、何时更新和怎样处理冲突仍由应用决定。[官方 Memory 概述](https://docs.langchain.com/oss/python/concepts/memory)

已读 `BaseStore` 源码确认：条目有 namespace、key、JSON value、创建/更新时间；可精确 get，也可做过滤与可选语义 search。语义索引依赖具体实现和配置，不能将普通 Store 存取说成默认已做语义召回。[BaseStore 源码](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint/langgraph/store/base/__init__.py)

官方提供 Postgres checkpointer、长期 Store 及对话裁剪/摘要示例。采用框架可选用现成持久化实现；保留当前自研 Runtime 也可只借分工，不要同时引入两套互不一致的会话权威状态。[数据库持久化及记忆管理文档](https://docs.langchain.com/oss/python/langgraph/add-memory)

对比赛的具体映射：

- 同一会话的消息与执行状态按 conversation/thread 管理。
- 跨会话任务按可信 user_id＋company_id 定位，而不是换会话就创建孤立副本。
- 偏好按用户与声明的适用范围管理；有效规则和业务数据仍属于各自模块。
- namespace 是组织与过滤参数，服务端还要校验可信归属；不能让模型任意提供命名空间。
- 框架检查点不自动等于业务写入幂等，数据库操作仍要有独立提交记录。

**判断：最值得借任务续办的状态模型；已有自研运行时不必为此全面替换成 LangGraph。**

## 八、OpenViking：借目录摘要与原文按需读取，后续规模化再评估整套引入

当前官方概念文档把上下文分为 resources、memories、skills；用户/peer 归属通过命名空间表达，会话提交可以启动异步记忆提取。不同接入方式是否自动捕获和召回要看相应插件，安装数据库不自动完成应用端调用。[上下文类型](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/02-context-types.md)、[会话与提取说明](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/08-session.md)

其 L0/L1/L2 分别为摘要、概览、明细。当前文档明确 L0/L1 主要是目录的语义 sidecar，并非每个文件必有固定三份副本；模型先定位内容，再按需读取原文。[分层上下文官方说明](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/03-context-layers.md)

当前检索说明包含来源 URI、可选查询规划、上下文预算、去重与分层装配。可以借鉴“先读概览、需要证据再读原文”，尤其适合未来大量规则与历史资料；本题少量短规则仍应保留完整条件，不只给模型一份生成摘要。[检索与上下文装配文档](https://github.com/volcengine/OpenViking/blob/main/docs/en/api/06-retrieval.md)

需要特别记录版本变化：README 仍可读到目录递归检索的介绍，而近期发布说明及 FAQ 已说明移除递归/父目录分数传播，改为限定范围的向量召回和统一重排。本文只借分层读取和可观察来源，不把旧宣传中的递归算法当当前实现。官方还自述项目仍处于早期，Stars 不构成生产成熟度验证。[官方发布说明](https://github.com/volcengine/OpenViking/releases)、[FAQ](https://github.com/volcengine/OpenViking/blob/main/docs/en/faq/faq.md)

DeerFlow 当前 OpenViking 适配说明限定为 middleware 模式、单 DeerFlow 用户与一把绑定 USER key；不能据可选后端的存在就认为该接入已覆盖我们的两用户两企业场景。[DeerFlow OpenViking 接入说明](https://github.com/bytedance/deer-flow/blob/main/docs/OPENVIKING.md)

**判断：值得作为长期上下文组织的参考，初赛完整引入的收益需要单独对照。分层读取与来源定位可以先在现有数据库上实现，整套引入还需核对所选版本许可与部署依赖。**

## 九、针对我们产品的推荐记忆结构

以下是结合赛题作出的设计建议，不是六个项目共享的标准，也尚未实现或测量。

| 逻辑层 | 保存什么 | 如何读取和更新 | 借鉴来源 |
|---|---|---|---|
| 当前任务 | 企业、月份、意图、待补字段、已提交操作关联、状态 | 按用户企业精确读取；依据本轮明确指令和真实工具结果同步更新 | LangGraph 状态/Store 分工、DeerFlow 任务接续 |
| 明确偏好 | 当前值、适用范围、稳定偏好键、原话来源、修订号、有效状态 | 明确用户表达才生效；更正原子替换；删除后旧抽取不能复活 | DeerFlow 写入筛选、Mem0 条目/历史、现有 RSI 来源版本 |
| 历史证据 | 原始用户消息、实际工具结果和操作记录 | 已知编号/来源精确读，其他必要信息按范围做文本/语义查找 | Mem0 检索解释、Graphiti episode 来源 |
| 可重建摘要 | 旧对话概览与定位原文的引用 | 有预算地提供给模型；来源变化即失效或重建，不覆盖权威当前状态 | Letta 常驻/按需、OpenViking 分层、DeerFlow 压缩钩子 |

当前任务字段和必要约束在每轮输入中有明确位置，不能与历史证据一起纯粹按相关性竞争后被裁掉。原始记录与业务数据分别保有权威，摘要用于导航和压缩。规则有效期与版本按规则模块读取，金额和缺用途清单按业务模块重新计算。

偏好源仅接受用户的明确原话；助手总结可以是派生材料，不能成为用户确认的替代证据。任务进度使用真实工具提交和当前查询结果，不能把助手说“已保存”的文本当最终依据。

## 十、最值得实施的升级与验证顺序

1. **范围和来源先固定。** 由服务端绑定用户企业范围；每个有效偏好有原话、来源版本和稳定键。保留现有 RSI 的 source/revision 检查，不因为引入第三方而退化成无来源摘要。
2. **任务状态与长期偏好分开。** 临时指令只作用当前任务；一次性授权不会变成长期开关。任务进度成功持久化后再回复，低影响整理可以后台运行。
3. **更正和删除形成完整生命周期。** 新值原子生效、旧值退出当前召回；删除拦截旧摘要、索引与后台迟到抽取；不能只删除一条向量。
4. **本轮输入分层并保留关键字段。** 当前任务和必要约束优先，近期完整消息组其次，历史按需。压缩前保存任务与必要明确事实，保留可核对来源。
5. **有漏召回证据再加强检索。** 同一套用例评估精确/文本基线，再增加向量或重排；观察新增召回是否同时引入跨企业、旧值或无关信息。

不建议首版照搬候选项目的自动偏好推断、全量用户画像、任意模型删记忆、访问热度淘汰、图数据库、后台自进化。上述能力与明确偏好、版本正确、资料可核对不是同一验收目标。

## 十一、用比赛案例检验“升级”是否成立

对照方案：近期窗口、近期窗口＋摘要、现有 RSI 式来源校验/文本召回、本文建议的分层与版本方案。保持同一模型、业务工具、数据和调用预算，冻结独立验收案例，不能让候选生成过程提前看到全部验收答案。

| 场景 | 必须观察的行为 |
|---|---|
| 用户在甲企业创建待办，之后切换乙企业 | 不混任务、偏好作用范围和规则 |
| 明确偏好在后续轮被更正 | 下轮和新会话使用新值，旧摘要不覆盖 |
| 删除偏好时旧后台提取仍在执行 | 旧结果不能重新创建已删有效偏好 |
| 用户只授权本次修改 | 后续会话不以记忆授权新的写入 |
| 加入长段无关聊天后再续办 | 企业、月份、待补信息与已执行结果保持正确 |
| 跨会话前其他人补完一张发票 | 恢复后重新检查，缺项反映当前数据 |
| 模型曾建议一个用途，用户没有确认 | 不把建议当用户事实或保存依据 |
| 召回失败或后台整理未完成 | 不假称已记住或已处理；必要时重新查询/追问 |
| 规则有新旧版本 | 查当前有效依据，不按语义相近或热度选旧版 |

分别记录任务完成率、重复追问、旧值误用、越权/错误写入、必要证据召回、输入 token、模型调用次数、耗时和费用。程序一致性测试与真实模型效果评测分开；本报告尚未运行上述对照，因此不报告提升百分比。
