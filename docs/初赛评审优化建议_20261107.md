# 初赛评审优化建议

## 最新工作区复审（2026-11-07）

结论：已具备赛题二主要能力和可演示基础，但不能宣布当前候选全面达标。评分标准没有给出及格线或细分评分锚点，不估算精确分数。以下基于当前源码、已有原始证据和本轮有限检查，不是正式比赛验收。工作区存在未提交修改，HEAD 不足以标识本次候选。本轮未修改业务代码、未调用真实模型、未重置业务库。

### 四个维度的判断

- **完整度（45%）：主要能力具备，整体验收未闭合。** Runtime、工具、冻结写意图、事务保存、回读与证据交付已经形成流程。request_checklist.py 已增加明确查询、用途检查和规则解释的交付检查，因此下文早期“新增清单”的建议已有实施。旧浏览器候选为21个检查点20通过、1失败；摘要失败遮蔽保存回执已另行修复，并有正常及故障注入两条真实模型浏览器复验。不能把不同候选结果拼成当前版本全量通过。复杂需求仍可能漏办。
- **契合度（20%）：方向契合，演示需聚焦。** 模型负责理解、追问和工具选择，程序负责权限、财务真值、规则适配、事务与核验；任务、显式长期偏好、规则、企业账本和聊天证据分开管理。应以一个完整办理例子解释这些设计，不只罗列模块。赛题一的自由SQL和经营洞察不应当作赛题二必做项。
- **完善空间（10%）：具备基础，范围有限。** 同一循环处理查询、解释和用途补全，已有规则版本与独立发票追加实例。但用途检查仅支持2026-09，启用规则受可执行模板限制，每用户每企业只有一个未完成任务槽。未经完整赛题材料比对，不能直接判为违规；也不能宣称任意业务可配置。
- **创新性（25%）：有工程组合价值，需证据支撑。** 最值得主张的是“可核验、可恢复的连续办理”：来源及版本约束、冻结写意图、同请求重放、跨会话重查、摘要失败仍交付真实回执。RAG、记忆库和工具调用本身不足以证明创新。需说明这些设计怎样减少漏办、重复修改和错误成功提示；历史探索对照不等于当前候选效果，也不证明行业首创。

### 优化优先级

1. **P0：冻结候选与统一验收。** 固定代码/前端指纹、非敏感模型配置、测试数据和证据目录。同一候选串行复核查询、规则、保存、响应丢失重试、跨会话续办及越权拒绝，同时核对页面、账本和数据库。程序测试、真实模型、人工确认分开记录。旧报告中“故障待修复”的状态应注明已由后续修复记录取代，原始失败不覆盖。
2. **P0：完成真实提交演示。** 使用连接后端的 `/showcase.html`：组合查询和规则 → 缺项检查 → 明确补充 → 保存回执与剩余项 → 同请求恢复 → 新会话续办 → 打开证据。frontend/src/demo.tsx 已标注概念示例，以定时器和本地状态展示模拟内容，不调用后端；demo.html 也不在当前 Vite 构建入口中。它可讲交互，不能证明主链路跑通。
3. **P1：补陌生表达与变更反例。** 事项清单是有限语法守卫，含糊的多企业多月份配对会跳过，写入不由清单授权。用独立预期的新题覆盖换表达、取消、部分成功、多个对象及并发revision变化，检查是否如实交付未完成事项。优先修实际失败，再扩任务规划。
4. **P1：优化异常表达及恢复指引。** frontend/src/api.ts 已处理HTTP/JSON异常，但原始fetch拒绝仍直接抛出，历史截图出现Failed to fetch。应区分受理前失败、受理状态未知和已提交后续失败；网络异常不能声称未保存，恢复需沿用原请求标识并查询真实状态。
5. **P1：记忆能力按验证范围展示。** 语义检索默认关闭；报告记录真实Agent三轮30/36、34/36、32/36，题目标签仍待独立人工确认。优先修复引用错选、旧日期未查历史和索引未覆盖却附无关引用。保留当前日期/词法搜索和覆盖不足反馈，不为演示直接开启未验收模式。

前两项直接影响完整度和创新展示，优先于新增OCR、更多模型、界面装饰或通用插件平台。

## 判断

可以优化。项目已经具备受控工具循环、任务与偏好分层、规则版本、保存核验、幂等和恢复基础。优先把这些能力形成可验证的任务闭环，而不是继续增加工具和模块。不能仅凭功能清单推算分数，也不能把其他赛题的经营洞察要求当作本赛题必做项。

## P0：让完整需求有完成判据

代码证据：backend/app/request_evidence.py 的 prepare_frame 主要绑定企业、月份和来源；backend/app/answer_renderer.py 的 _validate_delivery 明确仅核对已执行事项的交付；backend/app/tasks.py 当前为每用户每企业一个未完成任务槽。

风险：用户同时要求查询、解释和保存，模型可能只执行其中部分。已执行结果全部真实，并不代表整个请求完成。

建议在现有 Runtime 内增加本轮需求清单，先覆盖官方业务组合，不引入多 Agent。每项保留原话依据、目标范围、预期证据、状态和阻塞原因；模型提出拆解，程序校验范围与证据。最终答复区分已完成、待补充、执行失败、取消，不允许剩余项被整体 completed 掩盖。需求清单不能充当写授权。单轮清单与持久续办任务分开，避免直接重做现有任务槽设计。

限制：模型自己列出的清单也可能漏项，不能宣称程序已证明任意自然语言需求全部识别；还需独立预期和陌生组合问法。

验收建议：组合查询不漏企业或月份；查询并解释不漏解释；补用途并核验不漏核验；含糊对象必须追问；查询成功而保存失败须显示部分完成；用户取消剩余事项后不能继续执行。测试应检查证据及真实数据库状态，不只检查回复关键词。

## P0：冻结一份当前候选验收与提交材料

证据：README 的当前状态包含多轮历史结果和旧部署路径；docs/设计简述.md 仍写早期 62 项测试、模型尚待配置，与后续实施记录不一致。

建议：README 顶部仅给当前版本启动方式、有效入口、功能边界和本候选验收入口；历史报告归档链接保留。设计简述按当前架构重写。建立一份评审证据索引，将评审要求映射到真实操作、运行编号、规则版本、原始回执、预期值和失败记录。不同候选的通过数不要拼成同一版本成绩。

用固定候选和冻结数据完成官方主业务回归，再补组合需求、越权、重复保存、提交后断连及续办检查。模型测试、程序测试和人工复核分别记录。未重新执行前，不能把当前提交宣布为全量通过。

## P1：把已有保存可靠性做成可见演示

证据：backend/app/invoice_write.py 已有冻结修改计划、来源约束、revision、intent_hash 和 operation_id；这部分适合支撑“能完成操作”与创新性。

建议优先复用现有回执和运行详情，集中展示修改前后值、核验状态和剩余任务。现场演示提交成功但响应中断时，如何先查原操作回执；同一保存意图重试如何返回原结果；数据已被其他操作修改时如何要求重新核对。不要为了演示新增第二套写通路。

验收须分别证明：确实落库、回读一致、相同意图未重复修改、冲突没有覆盖新值。查询成功不能代替这些证据。

## P1：自然表达与事实核验分层

证据：backend/app/tool_schemas.py 的 FinalReply 和 backend/app/answer_renderer.py 使用受控结果块、说明码及宿主生成事实文本。这有助于可靠性，也使部分反馈偏机械。

先采用低风险改进：由真实状态生成“本次完成了什么、还缺什么、下一步需要你提供什么”。金额、票号、规则版本、保存状态仍由程序渲染；任务状态换成中文。不要直接开放不受约束的自由总结覆盖事实卡片。

如后续加入模型衔接句，限制其不能引入新的业务事实或成功承诺，并设计失败回退。自然表达应按准确、简洁、下一步明确进行人工验收，不按措辞多样性评分。

## P1：收敛记忆范围并如实处理搜索失败

证据：evals/conversation-semantic-v1/results.json 与 docs/CONVERSATION_SEMANTIC_IMPLEMENTATION.md 记录语义模式默认关闭；直接检索改写题混合结果为 19/20，但真实 Agent 三轮为 30/36、34/36、32/36。题目为合成草案，人工确认待完成。这些是不同层级结果，不能混称记忆准确率。

重点修复已记录的选择方案引用不准、明确旧日期未查历史、索引覆盖不足却附不相关引用。对未覆盖、无匹配、多候选分别反馈，不把未找到说成从未说过。

演示时明确四类信息：任务进度、显式长期偏好、有效规则、企业业务上下文；聊天原文搜索用于定位证据，不恢复旧写授权，不替代当前企业账本。语义模式先在隔离环境用新题和人工核验完成验收，再决定是否开启。

## P2：用已有多个场景证明统一流程

复用月度查询、规则解释、发票用途补充三个场景，展示同一套“确认范围—读取状态和规则—执行—核验—更新任务—反馈”的流程。补一个演示，展示换企业后规则不同、切换会话后任务可以继续。用途检查当前只支持 2026-09，这是当前范围限制；未经赛题材料核对，不能直接认定为违规或必须扩展至所有月份。

后续扩展基础应展示业务工具的输入输出、权限、规则依赖、幂等和核验接口。暂不为 10% 的扩展维度重写插件平台，不将新增数据库或模型数量作为创新证明。

## 建议的演示顺序

1. 一句组合需求，展示清晰的本轮事项及待办。
2. 查询结果与适用规则，说明数字和判断由程序核对。
3. 用户补充真实用途，展示保存回执与保存后重新检查。
4. 模拟响应中断或重复请求，展示回执恢复及没有重复写入。
5. 新会话继续任务，展示任务、偏好与旧聊天证据的不同作用。
6. 打开运行详情，核对来源、规则版本和真实工具记录。

这套顺序是建议，尚未实际录制或验收。创新主张宜集中为：可核验、可恢复的财税连续办理；用正常路径和故障反例证明价值。能支撑应用价值，不代表已证明行业首创或可预测比赛名次。

## 推荐实施顺序

先做本轮需求闭环及对应新反例，同时修正文档现状；然后统一回执和状态表达，完成固定候选主链路验收；最后补记忆失败与跨场景演示。OCR 扩展、更多洞察页面、更多模型及界面装饰暂缓，除非实际验收表明它们是主链路阻塞项。
