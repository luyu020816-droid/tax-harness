# 复赛整改 · 编码顺序与测试路线

配套 [整改 SPEC](./SPEC_复赛整改_八项能力与记忆架构.md)，版本 1.0，2026-11-20。SPEC 决定产品行为，本文决定先改哪里、如何证明问题已修好。**第一个交付是 S00：把两种旧库兼容升级到同一候选版本，并跑通四条业务入口。第一个业务修复是 S01：让用户说“只改这项”时，其他待办和写计划确实保留。**

## 从哪里开始

1. 记录 A `8af4d3919eb22b0b732c0aac7b2c979fa4f0b3b9`、B `e58b8bfa9ae0510828efb3e23484413072b00762` 和当前准备交付的提交号。用独立工作树从 A 整合 B，逐个处理两边都改过的模块；如果开始编码时已有共同后继，直接在该后继上重跑基线反例。原来主工作树上的两份复查和这两份文档也要带入交付树。不得通过整文件取某一侧而丢掉另一侧已验收的行为。
2. 建立隔离 PostgreSQL 测试实例。常规 fixture 使用 `tax_harness_test`，扩展 fixture 使用 `tax_harness_extended_test`。两者会清空测试表；所有worker、后台作业、前端服务均指向对应隔离实例。迁移测试另外新建不相互复用的临时库。不要让并行 pytest 进程共用一套会被清表的数据。
3. 每步按**红测 → 最小实现 → 原用例转绿 → 正例／并发／兼容回归**执行。红测必须因目标业务断言失败，环境缺失、连接失败或测试未收集不能作为基线。若在新的共同后继上反例已通过，保存用例和证据，跳过重复实现。下面的 `test_编号_…` 是新增用例的**建议前缀**，其余列出的测试文件均存在于 A 或 B。单步中有多项时，每项单独经历红绿循环。
4. 记录提交号、测试节点、输入、期望、实际、数据库关键字段和运行记录。脚本模型用来稳定制造错误工具参数，数据库断言检查后端是否守住边界。最后另用原页面和真实模型验证自然语言表现。历史探针在本机忽略目录；实施时应把最小反例转入仓内测试，避免依赖某台机器上的 JSON 或随机 ID。

## 分步编码卡

### S00 · 先统一版本与迁移

**先写红测。** 在 `backend/tests/test_agent_migration.py` 的独立临时库模式下增加 `test_int01_` 组。用固定的历史 DDL／可复现种子创建 A、B 旧库，切勿用修改后的当前 SQL 冒充旧版本。在两边分别插入可辨认的原始记录。B 库保留一条知识策略和带范围摘要，A 库保留工作簿结果和绑定任务的待确认写计划。断言升级保留这些对象；再构造编号齐全却缺一个关键结构的库，断言 ready 为假。

**再编码。** 对照 SPEC 的结构签名实现旧库识别、向前补迁、权限授予、同事务校验和就绪检查；合并两个分支的初始化、Agent 预置、工具注册、知识路由、任务与 UI。每个冲突以 A、B 各一条既有用例作约束。

**转绿后。** 跑空库、A 旧库、B 旧库、仅到 024 的两种中间库、并发启动和重复初始化。然后用运行账号读写策略、选择摘要、查工作簿、处理用途确认／取消。完成标准是旧数据内容和修订一致、完整库就绪、残缺库未就绪。集成失败回到迁移或组合逻辑修复；不得清空旧库重新初始化来判通过。

### S01 · 先阻止错关任务，再保证局部更新

1. **TURN-01**　在 `test_purpose_task_writes.py` 加 `test_turn01_`。造一个关联待确认计划的九月待办，让脚本模型对“不要取消，保留待办”发出带正确 ID、修订和引用的取消动作。先断言任务、计划、发票修订均不变。红测后修改动作授权和确认路径；再测明确取消、仅取消指定项和重复确认。
2. **AR-01**　在 `test_memory.py` 加 `test_ar01_`。旧任务含展示列与“待财务复核”，通过真实工具参数解析只改月份。断言保留这两项、旧检查引用标为待刷新。再改任务补丁和后台回写，覆盖省略、空字典、显式清除及读旧记录。检验后台结果没有把用户字段覆盖掉。
3. **AR-07**　在 `test_purpose_task_recovery.py` 加 `test_ar07_`。创建两件事、分别改／取消，换会话与企业，再重启读回。如果现有结构已能独立办理，录下证据即可。失败才按 SPEC 增加稳定事项身份和计划关联。在两项均存在时验证无明确目标会澄清。

**出步断言**　仅被授权的任务／事项及其未执行计划发生变化。旧计划引用过期修订时拒绝，已提交的发票仍可按原操作号核对。

### S02 · 先约束写入，再处理读取与同义更正

1. **MEM-01**　在 `test_memory.py` 加 `test_mem01_`，通过 ScriptedModel 和正常 tool dispatch 复现“不要记住”和“原文简短、工具值详细”。断言零有效写入。编码后补正常记住、表单维护、明确更正、删除、重启，以及来源已变的确认请求。
2. **MEM-02**　同文件加 `test_mem02_`；`test_phase_two_acceptance.py` 补摘要与原入口读取。材料只标“仅甲企业”，检查 U001/甲、U001/乙、U002 三方。先让错误全局范围受阻，再在 fixture 中保留一条旧版误归类的记录。撤销甲的权限后，乙的普通问题必须能继续，列表／模型输入／摘要均没有旧标记，合法全局格式仍可见。
3. **AR-02**　加 `test_ar02_`，用两个会话和两个合法英文键写“简短→改为详细”，断言只更新原对象。实现稳定维度和冲突消歧。用“正文简短、附录详细”做反向对照，再测两个旧值冲突、并发更正、同请求重放和旧数据迁移。

**出步断言**　同时查偏好表、修订历史、原页面列表和实际请求中的正式偏好。历史修订的保留和当前有效值应分别断言。

### S03 · 锁定计算口径和币种

1. **FILE-01**　在 `test_workbook_query.py` 加 `test_file01_`，用 openpyxl 写真实 XLSX，绑定 SPEC 中的三行及原坐标。先向正常查询入口给错月、错类别和遗漏分组；断言无成功结果 ID。实现口径校验后，断言总额 57.42、交通费 12.30、住宿费 45.12 和十一月 123.40 对应的实付列、行号、范围均准确。
2. **FILE-02**　加 `test_file02_`。同表 C2=120、D2=CNY、C3=10、D3=USD。先断言错误定位第 3 行且无人民币合计，再实现币种证据、快照版本及旧文件重解析。把 USD 换为 CNY 后合计 130.00；补显式币种列为空、带外币数字格式及无币种列的旧人民币模板。

**出步断言**　跑原有“上传→查询→追问→查看原行→撤权”用例。Word 和文字型 PDF 上传解析的原测试保持通过。S06 改动后还要用未来版文件重复这组测试。

### S04 · 先实现核实原操作，再接续办按钮

**红测。** 在 `test_purpose_task_recovery.py` 和 `test_mutations.py` 增加 `test_rec01_`。用事务边界的受控故障分别覆盖“已有 prepared、业务提交前失败”“提交成功、回读失败”“服务端提交成功、浏览器没收到响应且进程重启”。记录 F002 初始修订、用途、计划和操作号。

**实现。** 让错误经过 runtime 和 API 后仍带原操作号，向原办理页提供核实动作；根据操作状态提供允许的下一步。复用原校验服务和业务事务，对同一计划复用同一指纹。覆盖双击、原计划已取消和恢复期间数据库仍不可读。

**出步断言**　原页面可以找到操作号。核实不增加发票修订，合法续办至多增加一次。已提交只返回原回执，待确认仍待确认，未知时如实返回未知。运行已有回执丢失场景和前一步任务范围用例。

### S05 · 冻结模型，再裁剪失效能力

1. **AG-01**　在 `test_agent_runtime.py` 和 `test_agent_models_db.py` 加 `test_ag01_`。用可区分的两个适配器，设置并发屏障在请求甲已受理、worker 尚未领取时切换 A→B，再受理乙。断言首次领取、重领和运行详情的版本与各自受理绑定相符。实现激活版本持久化与 resolver 后，重建 worker，覆盖旧凭据不可用的显式失败。
2. **CAP-01**　在 `test_agent_authority.py`、`test_agent_context.py` 加 `test_cap01_`。两个 Agent 共用 Skill，停用必需工具，检查实际 schema、系统指引及直接执行三处。修运行时依赖交集和预览。恢复启用后新请求成功，其他原有权限始终保持。

**出步断言**　配置变更前、变更后和恢复后分别保留一份模型实际输入；失败的连接测试不会推进默认版本。旧执行不能因为重新启用工具而扩大原授权。

### S06 · 日期解释与版本选择在所有入口保持一致

1. **KB-02**　在 `test_knowledge.py` 或 `test_knowledge_natural_answer.py` 加 `test_kb02_`。三种日期写法使用同一授权资料、同一受控模型参数。先断言相同的查询时点，再实现解析和冲突判定。输入非法日期或两日期无从判定时检查追问。
2. **KB-01**　在 `test_knowledge_file_lifecycle.py` 与 `test_workbook_query.py` 加 `test_kb01_`。固定业务日期：9 月 20 日、11 月 19 日、12 月 1 日。准备 V1、未来生效 V2 和一个仅 ready 的候选。先写“发布 V2 当天仍命中 V1”失败用例，再实现发布记录、按时点选择、引用回读和工作簿有效版本校验。

**出步断言**　详情、检索答案、引文定位、工作簿及原文件查看指向同一适用版本。未来版生效无需重启，停用和撤权立即生效。覆盖旧发布记录不完整、并发发布、受规则引用的文档、月内换版及重复上传。

### S07 · 先缩小入模集合，再缩小失效范围

1. **AR-05**　在 `test_context_limits.py` 加 `test_ar05_`。固定同一 Agent、工具及预算 16,000，创建一个空会话和 20 条带适用附表的偏好。先证明日常问题无法装配，再实现按适用场景加载。在同一条件下验日常问题能发送、查询第 3 类附表时有正确模板、全局强制限制仍在。保持预览标明估算。
2. **AR-03**　在 `test_conversation_context.py` 加 `test_ar03_`。修改月报格式前后比较“一周有几天”的历史投影和原文。另建确实引用旧偏好及已撤权来源的样本，分别断言必须保留、必须失效的内容。改输入清单与派生依赖的职责，再复验审计展示和旧格式清单。
3. **AR-04**　在 `test_runtime.py`、`test_context_compaction_flow.py` 加 `test_ar04_`。控制事务交错：乙请求领取后甲写偏好、乙请求装配后新增适用限制、旧摘要生成时来源变更。核对原 turn 是否完成、重装次数、晚到摘要能否发布和业务写入次数。实现范围版本后，重跑 S02 的撤权矩阵及 S04 全部恢复测试。

**出步断言**　无关变更不打断当前请求，相关变更不允许用旧授权提交。不能靠放宽 `guard`、删除来源检查或增大模型窗口使测试转绿。

### S08 · 先保护摘要内容，再让压缩及时发生

1. **CTX-02**　在 `test_compaction.py` 加 `test_ctx02_`。长首句后加入“不得外发。票号F002尚待核对。”给定 1,024 锚点预算，脚本摘要故意遗漏这两句。先断言不能错误标记完整覆盖，再实现优先级、逐条覆盖校验和安全回退。复验更正后的 F002 与被撤回来源。
2. **CTX-01**　在 `test_context_compaction_flow.py` 加 `test_ctx01_`。预算 16,000，前五组对话各 2,200 个中文字符，第六轮继续处理 F002。自动压缩和手动入口分别断言能推进。实现预算预判及完整组选择，再测不可分割当前输入超长、工具调用与结果配对、压缩失败后的可读状态。

**出步断言**　保留实际发送 payload，核对预算、待办、限制和有效回读入口。用 S07 的“没有历史仍超预算”用例确认两类问题都已关闭。

### S09 · 明确回顾历史时再开放检索

**红测。** 在 `test_conversation_context.py`、`test_agent_context.py` 加 `test_ar06_`，给三个场景固定同样的历史材料，分别发普通问候、明确要求回顾昨日会话、由已禁用历史能力的 Agent 发相同回顾请求。记录实际系统指令、工具集合、派发结果和渲染回复。

**实现与转绿。** 让同一策略驱动上述四个入口。复验当前会话原文与摘要回读、跨会话显式授权、另一用户、知识范围受限的 Agent、停用资料、索引不全和旧游标。启用模式下不能让模型遵循提示后又被回复渲染器拒绝。

### S10 · 原入口联验与交付

在独立候选服务的 `/showcase.html` 固定代码提交、模型标识、预算、模拟数据和两个身份。先以脚本模型跑稳定回归，再以真实模型从输入框／管理页操作。第三方可用以下四条连续场景复验：

| 场景 | 操作 | 应同时检查的证据 |
|---|---|---|
| 甲乙企业与两个 Agent | 甲保存限定偏好，换乙、换用户、新会话；管理页停用共用工具，发布新默认模型，随后恢复 | 各身份的有效偏好、两名 Agent 的模型版本与工具指引、实际输入和回复 |
| 两项待办及故障恢复 | 要求 A、B 同时待办，补充字段，只改 A，明确保留后再取消 B；原已授权保存注入响应丢失，重启核实 | 每项状态／修订、关联计划、唯一操作号、发票版本、原页面回执 |
| 文件和制度换版 | 上传标准 Excel、Word、文字型 PDF，核对行／段／页；重复上传，尝试他人更新；提前发布 V2，并在前后日期查同一条款，再停用 | 业务金额、文件版本／币种／坐标，检索来源及回读状态、停用后的模型输入 |
| 长对话、记忆和明确回顾 | 混合大材料、长前缀、限制与待办，触发压缩；跨会话更正偏好、回读原话并切换企业 | 预算和实际 token、锚点来源、当前有效值、相关和无关会话是否继续、用户最终可见答复 |

每个案例保存四种证据：原页面输入与回复、turn/run ID 及实际模型输入、工具参数与结果、前后业务状态或操作日志。真实模型增加不同措辞，记录失败与再次运行。真实服务未配置、浏览器用例跳过、索引不就绪或缺少依赖时标为未测／受限并注明影响范围。不得将修复前的观测数值当作修复后的结果。

## 执行命令与验收记录

下列 PowerShell 命令以依赖已安装、测试库已配置的**统一工作树根目录**为起点。示例使用项目的 `.venv`，如两个工作树共用仓库既有虚拟环境，将 `$testPython` 指向对应的 Python 3.12+ 解释器。S00 的新测试写好后先单独运行迁移反例；S00 完成后再执行后面的 S01 测试。

```powershell
$testPython = (Resolve-Path '.venv/Scripts/python.exe').Path
Push-Location backend
& $testPython -m pytest -q tests/test_agent_migration.py -k int01
& $testPython -m pytest --collect-only -q tests/test_purpose_task_writes.py tests/test_purpose_task_recovery.py tests/test_memory.py
& $testPython -m pytest -q tests -k 'turn01 or ar01 or ar07'
& $testPython -m pytest -q tests/test_purpose_task_writes.py tests/test_purpose_task_recovery.py tests/test_memory.py
Pop-Location
```

各步在 `backend` 下使用下列 `-k` 表达式。新增节点尚不存在时 pytest 可能选择零项；开工时先建立对应失败用例，记录收集到的测试数。每步转绿后运行该步编码卡列出的整个测试文件，再运行受牵连的前序文件。完整离线回归使用仓库现有脚本。

| 步骤 | 新用例筛选词 | 必查的跨步回归 |
|---|---|---|
