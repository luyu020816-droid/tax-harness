# Session 上下文、压缩与缓存策略 SPEC

状态：已实现主要链路，等待用户人工验收。版本日期：2026-11-11。基线：`feature_adjust_1107`。本文替代 `SPEC_Session上下文与压缩_2026-11-11.md` 中冲突的预算、触发及手动压缩设计；旧文档保留以便追溯。范围是上下文内核，输入框环形和 `/compact` 是其客户端入口，不决定内核策略。

实施核验：隔离库覆盖自动/手动压缩、用户隔离、幂等、失败保留与业务回归；真实 DeepSeek 模型完成合成对话摘要及后续问答。本机演示库已备份、迁移并移除旧的显式 16K 上限。现有估算仍为 UTF-8 启发式，草稿预览可能与执行时上下文不同；15,100 Token 低上限下，金额与完整规则同轮场景已确认可能安全失败。切换到未经确认容量的模型时仍按保守上限处理，不能据此声称所有模型和超长对话均已验证。

## 1. 目标和边界

同一个 Session 可以长期保存聊天记录，但每次模型调用只发送经授权、按当前状态组装的一个上下文视图。默认项目目标窗口 100,000 tokens；在确认模型容量和配置允许时充分使用此窗口，压力接近 90% 时自动压缩。支持用户输入完整命令 `/compact` 手动请求压缩，输入框旁显示可解释的估算占比。

压缩只替换后续模型上下文中的旧消息视图，不删除原始历史、业务数据、操作回执或知识库资料；删除与权限变更仍按现有规则执行。聊天历史、知识库、业务规则保持现有隔离。摘要是导航材料，不是新事实或写入授权；准确数字和当前业务状态必须重新核对。来源完整和格式校验不能证明摘要语义零丢失。

非目标：重写 Agent runtime、搬迁数据库、强制统一所有服务商的缓存实现、为追求命中率削弱鉴权或追求最低时延；不保证任意长度内容或任意摘要都可以无损保留。

## 2. 实际现状与待修正点

| 项目 | 当前代码事实 |
| --- | --- |
| 有效输入预算 | `Settings.context_budget = min(INPUT_BUDGET, floor(MODEL_CONTEXT_LIMIT×0.95)-OUTPUT_RESERVE)`；默认 `INPUT_BUDGET=16000`。现有本机环境还**显式**配置了 16000。 |
| 自动压缩 | `context.assemble` 超预算，或大于预算 85% 且历史估算大于 4096 时，选择较早组；`runtime` 最多尝试两次摘要。不是 100K 的 90%。 |
| 近期对话 | 代码优先保留最近 5 个有效对话组；极端容量不足仍可能去掉这些组内的工具片段或报错。不能声称五轮永远完整且必然可发送。 |
| 计量 | `context.estimate_tokens` 估算序列化 UTF-8 字节数除二与消息开销；不是精确 tokenizer，也不能保证对所有模型都高估。 |
| 压缩 | `compaction.compact` 分批生成摘要、校验来源并发布；当前摘要正文本身有 2000 字符限制，另有受保护摘录。它不保证语义无损。 |
| 缓存 | 动态正式状态进入第一条 system 内容；工具定义因请求条件变化。它们可能改变请求前缀，实际命中率需测量。 |
| 切换模型 | 页面切模型时 `model_connection._candidate` 对不同模型由 16K 预算推算 `model_context_limit`；该推算不能被标成模型已确认容量。 |
| 输入字符 | 前端和 `turns.accept_turn` 的单条 16,000 **字符**校验与 16,000 **token** 输入预算是两个限制；本次保留字符限制，不混为一谈。 |

公开资料：DeepSeek 官方声明 V4 Flash / Pro 的官方服务支持 1M 窗口；本机检查到地址为 `https://api.deepseek.com`、模型为 `deepseek-v4-flash`。这只能作为该官方路由容量的资料依据，实际服务可用性、别名变化及其他兼容服务仍需核验，不能将 `1000000` 宣称为所有接口的实测值。[官方发布说明](https://api-docs.deepseek.com/news/news260424/)

## 3. 参考与设计选择

[DeepSeek Harness compaction-basic](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/compaction/compaction-basic/README.md) 当前按模型窗口、输出预留和额外余量决定阈值，先压旧的闭合组，保留近期内容；提供手动压缩、溢出恢复和切模型时容量检查。其默认公式为 `floor(min(W×0.8,W-O-B))`，`B=65536`，近期原文默认预算为 `(W-O)×0.16`；这些是其插件默认值，不是通用最优值。按我们的 100K 窗口照搬大余量可能导致过早压缩，因此不照抄。

可选方案：A. 保留 16K 输入上限，实施简单但无法实现目标；B. 直接把预算改为 100K，改动少但缺输出预留与溢出保护；C. 按真实模型窗口和项目上限计算单次可用预算，保留安全余量并按实际压力压缩。**选择 C**。近期以至少 5 个完整对话组为保护目标，而非照搬其 16% 的长度比例；容量不足时明确失败。

[DeepSeek Harness 动态上下文说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/system-prompt.md) 和 [OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching) 提倡稳定可复用前缀。我们优先让稳定指令和工具描述保持稳定，但任何缓存优化必须保持当前权限、范围、来源与写入保护，不能为了缓存复用遗漏或延后强制状态校验。

## 4. 单次调用预算：唯一口径

### 4.1 符号和计算

- `C`：当前 provider + model 对应的可信上下文容量。来自经明确配置的模型容量或该精确官方路由的版本化能力登记，必须记录来源；推算值不视为可信容量。
- `T`：项目目标窗口，默认 `100000`。`W = min(T,C)`；不可超过服务商容量。
- `R`：该次模型调用的实际 `max_tokens`，默认沿用 `OUTPUT_RESERVE=2048`；推理 token 如服务商计入输出也需计入此值。
- `M = max(2048, ceil(W×0.05))`：协议和估算误差余量。`R` 不能再在其他环节重复扣除；`M` 是安全余量，不是精确计数保障。
- `H = W-R-M`：输入硬预算。校验 `H >= 512`；不足时配置错误，不发请求。
- `L`：可选、显式的 `INPUT_BUDGET`。当设置时 `H_effective=min(H,L)`；未设置时不再暗中套默认 16K。区分缺省与显式设置。
- `E = H_effective+R+M`：展示与压缩使用的**有效等效窗口**；无额外限制时 `E=W`。如果显式 16K 限制存在，不能以 100K 分母掩盖它。
- `I`：本次完整模型请求的输入 token 估算，含系统、工具 schema、状态、摘要、历史、本轮消息及本轮工具结果；不含 `R`、`M`。
- 压力 `P=I+R+M`，环形显示 `P/E`；超 100% 保留真实百分比，环形视觉最大 100%。
- 自动触发：`P >= ceil(0.90×E)`；硬约束：`I <= H_effective`。当已知下一步最小必要输入会超限时可提前进入同一压缩流程，不以 UI 数值为判断依据。

| 场景 | W | R | M | H_effective | E | 达到 90% 的 I |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 目标 100K，无额外上限 | 100000 | 2048 | 5000 | 92952 | 100000 | 82952 |
| 目标 100K，显式 16K 上限 | 100000 | 2048 | 5000 | 16000 | 23048 | 13696（向上取整） |
| 模型仅支持 32K，T=100K | 32000 | 2048 | 2048 | 27904 | 32000 | 24704 |

本地 `.env` 已显式 `INPUT_BUDGET=16000`。新代码不能擅自忽略它；根据用户已明确提出的 100K 目标，实施并通过隔离验证后，针对本机演示环境移除此项，或显式配置期望的更大输入限制，并重启读取环境的服务。其他部署的显式限制继续生效。新默认放开不等于已有环境自动迁移；保留 16K 的环境在界面明确提示限制来源。修改配置不得打印或提交密钥。

### 4.2 窗口未知与模型变化

容量未知、仅推算或与 provider/model 不匹配时：显示“模型容量未确认”，保持现有保守输入预算与模型调用能力；不展示虚假的 100K 百分比。保守预算只作为配置上限，不能证明小于未知服务商真实限制。提供明确配置或可验证能力登记后才切换至目标预算。

给已接受任务固定 provider、model、容量来源、预算和版本快照；运行期间页面切模型不能改变该任务。密钥不得写快照。对新任务按新模型重新计算，旧配置的容量不得自动继承给不同路由。切到小窗口时，下一请求先按新窗口检查并安全压缩；若无法满足，明确失败并保留旧记录和摘要。切模型不保证复用旧模型 KV cache。

### 4.3 估算和组装

提取可复用的纯投影 / 组装与计量逻辑，运行时和预览使用同一计数函数、同一工具/消息序列化方式及预算计算。请求预览是只读、无模型调用的草稿估算，不创建 turn、source、summary，不伪造 `Execution` 或绕过 `execution.guard`。

实际运行仍须重新加载正式状态、权限和证据，生成真实 `request_frame`、附件及当前工具状态，并执行原有 `guard`/`validate`。预览无法在受理前完整确定 source ID、引用、附件状态或未来工具结果；使用明确占位/当前可读取状态并返回 `approximate=true` 和不包含的项目。不得承诺预览与未来真实请求逐 token 一致。不可用时显示未知，不用 0% 冒充。若统一预览会扩大安全边界，先保持受保护字段组装在运行时，抽取共享纯组件，不削弱校验。

计数器优先使用与当前 provider/model 对应且可用的 tokenizer；否则沿用并标记 `estimated:utf8_div2_plus_protocol`。服务商已返回的 usage 是**已完成请求的实测**，不能当作当前草稿精确值；预览和实际发送均记录计数方法版本。估算偏差依旧可能触发 provider 超限，需要有限恢复。

## 5. 自动压缩：完整链路

```text
本轮新问题 / 工具返回
  → 权限和范围核验 → 组装当前请求 → 计算 I、P 和硬预算
  → 未达触发条件且未超限：调用模型
  → 达到触发条件且有可压缩旧组：生成并验证摘要
  → 原子发布成功：重新组装、重新计量，再调用模型
  → 无可压缩组且不超硬预算：按原样继续，并记录原因
  → 超硬预算但无法安全压缩：明确失败，不丢失原文
```

1. 以 Session、用户、当前企业范围、`memory_epoch`、活跃摘要版本及来源 revision 确定候选。原有公司授权、引用、epoch 和来源失效检查继续生效。
2. 从最旧到最新选择尚未覆盖的**完整闭合组**；工具调用和对应结果不得拆开。保护当前请求、本轮已接收工具结果、未闭合工具组、待确认写入及最近 5 个有效对话组。保护范围本身超限时返回 `CONTEXT_CAPACITY_EXCEEDED`，不偷偷删近期用户/助手消息。
3. 在有限模型调用预算内分批合并旧摘要和候选组；每个摘要请求自身也必须满足摘要模型容量与输出限制。保留主体、企业、时间、数值、更正、否定、未完成事项和操作真实状态，拒绝把不可信历史当指令。
4. 延用并加强来源 ID、revision、权限、保护摘录、摘要结构及闭合性校验。要求新摘要覆盖被选择的来源；比较压缩前后同口径估算，必须实际缩小，否则返回 `COMPACTION_NO_GAIN`，不发布虚假成功。
5. 同一事务中重新核验 lease/fence、会话状态与范围、用户授权、`memory_epoch`、来源 revision、旧摘要 generation；任一变化则废弃候选。原子切换旧摘要状态、写新摘要和操作结果。绝不能先让旧摘要失效再单独提交新摘要。
6. 重新组装计量；保留不下时最多一次额外压缩尝试，仍不满足则明确失败。压缩不保证一定降到 70%，最近原文与必要状态优先，避免循环反复压缩。

超时、摘要无效、模型出错或进程崩溃时旧摘要和原文仍可用。provider 明确报告上下文超限时，最多执行一次有界压缩并重试一次；不能靠反复重放业务工具恢复。已提交业务写入沿用原操作回执和幂等核验。

## 6. 手动 `/compact`：受控操作，不是聊天

输入框仅在 `draft.trim() === '/compact'` 时触发，大小写保持精确；`请解释 /compact` 是普通消息。带附件时不自动丢附件、不提交命令，提示先移除附件或另发；输入法组合、Shift+Enter 和普通发送保持不变。

使用现有 `turns.request_kind` 扩展 `compact` 的持久化任务，而不是在 HTTP 线程伪造运行中的 execution：

- 数据迁移在停止旧 worker 后替换 `turns` 现有 `request_kind` CHECK，保留 `chat`、`write_confirmation` 并加入 `compact`；遵循项目迁移版本机制，迁移失败不启动新 worker。
- `POST /api/v1/sessions/{id}/compactions`，body 为稳定的 `client_request_id`；复用已认证用户、会话所有权、可访问企业、归档/删除限制和 admission。成功返回 `operation_id`（对应任务）、状态与查询地址。
- 使用实际 turn、source、work item、run、lease、generation、fence 和 heartbeat 接入现有 worker，按该用户现有队列串行；同一 Session 的聊天与压缩不能并发发布，跨进程依赖数据库锁及 fencing，不依赖前端或进程锁。compact 控制 source 是内部标记，不作为普通聊天内容或写入授权，也不进入知识库或对话投影；其评估/进度应以独立控制类型完成，不能堵塞记忆进度。
- 相同用户的同一个 `client_request_id` 及相同 Session 幂等返回原任务；同 ID 不同内容返回冲突。用户重复点新 ID 时，若该 Session 已有排队或运行的压缩，返回已有任务，避免重复工作。网络状态不明时客户端保留相同 ID 查询/重试。
- 复用第 5 节的选择、模型、保护、校验与发布，手动不要求达到 90%。无可压缩较早组返回 `no_content`，不调用模型；模型失败返回 `failed`，不声称成功。
- 状态：`queued / running / succeeded / no_content / failed / cancelled`。`GET /api/v1/sessions/{id}/compactions/{operation_id}` 按当前身份重新鉴权，返回前后估算、时间、摘要 generation/覆盖边界和脱敏错误。被删除、越权或范围失效时不可读取敏感内容。
- 摘要发布与成功状态在同一数据库事务提交，以 operation ID 关联发布记录；重启接管前先检查是否已发布，避免提交成功但回执丢失后重复发布。未提交候选不得对外可见；租约过期通过 fence 防止旧进程提交。用户取消、会话删除、企业切换、撤权、原文更正都必须使过期候选无法发布。
- 与自动压缩竞争时沿相同会话互斥规则，状态可排队；任务结束后不生成普通 assistant 回答或混进历史轮次，但保留可审计操作事件。审计和会话消息接口、source 进度、恢复流程必须适配新类型。

## 7. KV cache：独立优化、实测而非承诺

底层历史追加不等于每次发给模型的前缀追加。普通聊天尽量稳定 system 指令、工具定义及既有对话顺序；需要变化的业务状态如能安全地以明确的受信任状态消息放在后部，经过适配器与 `context.validate` 调整后再引入。旧状态不得覆盖新状态；格式、消息角色或模型行为不兼容时保留原实现，安全优先。

本期不为缓存牺牲工具最小授权或删除现有工具过滤；先测量变化带来的影响。不得假设 Chat Completions 具备其他 API 的 `allowed_tools` 或服务端 compact 能力。压缩会改变被替换位置及其后面的可复用前缀；换模型、变更工具 schema 或 system 内容也可能造成缓存不命中。不同厂商规则不同，不能保证 100% 命中。

利用已有 `context_snapshots.usage`，若 provider 返回 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens` 或对应嵌套字段，统一记录实际值、model/provider 标识、input tokens 和计数来源；无字段为 `null`，不是 0。仅在分母存在且大于 0 时计算 `hit/(hit+miss)`。洞察展示当前用户有权查看的单次/聚合数据；不记录 API key、完整提示词副本或跨用户内容。通过同一模型同一测试会话的连续请求观察命中、压缩前后及模型切换，不能用模拟调用当真实缓存数据。[DeepSeek 缓存规则](https://api-docs.deepseek.com/guides/kv_cache/)

## 8. UI 附属层

在 `frontend/src/App.tsx` 现有 composer toolbar 内添加紧凑环形，不改变现有页面布局和配色。显示 `上下文 42%`；使用键盘焦点或点击打开小提示，显示估算输入 I、R、M、E、计量方式、配置来源、限制状态及最近压缩结果。无 Session、容量未确认、预览失败显示 `上下文 --` 和原因。

草稿防抖发送只读预览，前端携带版本并丢弃旧响应；Session、企业、模型、摘要或轮次变化重新请求。环形为信息展示，不提供压缩决策；前端失败不影响普通聊天发送。`/compact` 提交后呈现排队、压缩中、成功、无内容或失败及可核验前后估算，刷新后可查询状态。界面不伪造完成进度，支持键盘和屏幕阅读器，窄屏保持可用。
